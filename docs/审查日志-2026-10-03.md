## 一、总体结论（大白话）

两条核心链路的**主路径是健康的**：28 项自动化测试（含 GPU 真实推理集成测试）全部通过，下载落盘、增强合成、格式转换的常规流程经过实测验证没有问题，工程质量在同类项目里属于上乘。

但发现了 **3 个严重问题（P1）**：都藏在"异常场景"里——正常用没事，一旦碰上就出事。其中两个直接打在产品的核心卖点上：

1. **断点续跑在最该它的场景（关机/断电/崩溃）失效**——README 首屏承诺"关机、睡眠、崩溃都不怕"，实测恰恰是这三种情况进度无法恢复（已用模拟实验实锤）。
2. **批量下载多个 m3u8 链接会互相写坏文件**——两个任务用了同一个文件名（已实测：3 个连续任务生成了完全相同的名字）。
3. **抽帧阶段被中断后恢复，会生成"缺帧的半截视频"**，而且用户很难察觉。

另有 8 个重要问题（P2）、13 个建议项（P3）。**没有致命问题（P0）**——不存在"一点开就崩"或"必然损坏"级别的缺陷。

| 分级 | 数量 | 一句话概括 |
|---|---|---|
| P0 致命 | 0 | — |
| P1 严重 | 3 | 断点续跑失效（关机场景）、m3u8 批量同名互写、恢复出半截视频 |
| P2 重要 | 8 | 文件名虚标倍数、损坏帧不校验、日志无限增长、潜在崩溃点等 |

## 三、P1 严重问题（3 个）

### P1-1 断点续跑在关机/断电/崩溃场景失效（核心卖点不兑现）

- **位置**：`app/enhance.py` L117-139（`find_interrupted_jobs`）、`app/main_window.py`（无 `closeEvent`）、`app/main.py`（无 `aboutToQuit` 处理）
- **原理**：档案状态机只有两个转换路径会写入 `interrupted`：任务**抛异常**（`_video` 的 `except` 分支 L335 `mark_job`）和**用户主动取消**（`CancelledError` 同样走该分支）。而**进程被直接杀死**（关窗口、Windows 关机、断电、任务管理器结束进程）时，工作线程没有任何机会执行 `mark_job` —— 档案永远停留在 `running` 状态。而 `find_interrupted_jobs` L134 的过滤条件是 `d.get("status") != "interrupted"` 就跳过。
- **实测证据**（本次审查模拟实验）：构造 `running` 状态档案 + 20 帧已完成现场 → `find_interrupted_jobs` 返回 **0 个**可恢复任务。进度明明都在磁盘上，界面却永远不会提示恢复。
- **影响**：README 首屏明确承诺"增强一个长视频的中途，**关机、睡眠、崩溃**都不怕，下次打开点一下「恢复任务」接着算"。实测只有"失败"和"取消"两种情况兑现；**"关机/崩溃"恰恰不兑现**。用户算了几小时的帧变成无人知晓的磁盘垃圾。这直接复刻了 `docs/审计报告.md` 第六节 2026-09-29 事故的痛点（那次靠 v1.1 的档案机制兜底——但兜底只兜了一半）。
- **附带缺陷**：主窗口关闭时不阻止、不提示、不等待运行中的任务（无 `closeEvent`），任务正在跑时点 X 直接退出，加剧上述问题。
- **修复思路**（供参考，未执行）：最省事的一行级修法——`find_interrupted_jobs` 把 `running` 也视为可恢复（反正 `total`/`done` 都是档案里已有的信息）；稳妥做法是再补 `closeEvent`：有任务在跑时弹确认框，退出前把 `running` 档案标记为 `interrupted`。

### P1-2 批量下载多个 m3u8 链接时文件名冲突、互相写坏

- **位置**：`app/download_tab.py` L610-613（创建 `M3u8DownloadTask` 时**不传 name**）→ `app/m3u8_dl.py` L31 `save_name = self.name or f"视频_{now_tag()}"`，`now_tag`（`app/utils.py` L73）**精确到秒**。
- **原理**：批量粘贴多个 m3u8 链接点「开始下载」时，`_spawn` 循环毫秒级连续启动最多 3 个任务；排队任务在 `_on_thread_end` 的 while 循环里也是同秒连续拉起。多个 m3u8 任务的 `save_name` 极大概率**完全相同** → 两个 N_m3u8DL-CLI 进程拿到相同的 `--workDir` + `--saveName` → 在同一个 `Downloaded/saveName/` 目录里下载分片（`000001.ts` 等同名分片互相覆盖）→ 合并产物是两个视频的混杂体或损坏文件。
- **实测证据**（本次审查模拟实验）：连续创建 3 个 `M3u8DownloadTask`，三者 `save_name` 完全相同（`视频_20261003_123842` × 3）。
- **影响**：批量 m3u8 是 README 明确支持的场景（"批量粘贴：一次粘贴多个 URL"）。触发概率高（同秒启动），后果是**静默数据损坏**——下载显示"成功"，文件内容却是坏的。
- **附带**：m3u8 永远拿不到 `name`（解析预览卡片只服务 `site` 引擎），100% 依赖时间戳兜底。
- **修复思路**：`save_name` 兜底时在时间戳后追加任务 ID 或 URL 哈希（如 `视频_20261003_123842_a1f3`）；或从 URL path 推导名字。

### P1-3 抽帧阶段被中断，恢复后生成"缺帧的半截视频"

- **位置**：`app/enhance.py` L306-307（抽帧**前**写档案 `total=0`）→ L313-314（抽帧**后**重写 `total=帧数`）；`ResumeTask.run` L390-393 的补抽条件 `if total_expected and have_in < total_expected`。
- **原理**：若进程在**抽帧阶段**被中断（断电/强杀/取消恰好落在这个窗口，长视频抽帧可持续数十秒到几分钟），档案里 `total=0`。恢复时 `total_expected=0` 为假值 → **跳过补抽帧** → `total = _count_frames(frames_in)` 把不完整的帧数当成全部 → 只增强这部分帧 → 合成的成品**时长短于原视频**，音频却照拷全片（`-map 1:a?`）→ 音画严重不同步 + 内容丢失，且文件能正常打开播放，用户极难察觉。
- **影响**：与 P1-1 叠加时（关机场景档案停在 running 且 total=0）形成"双杀"。单独看：即使档案被正确标记 interrupted（主动取消路径），抽帧中途取消同样会触发。
- **修复思路**：档案增加"抽帧完成"布尔位（或约定 `total>0` 才算完成）；恢复时抽帧未完成则无条件重抽（`extract_frames` 带 `-y` 全量覆盖，代价可接受）。

## 四、P2 重要问题（8 个）

### P2-4 真人视频 3x/4x 选项：实际输出 2x，文件名却虚标"高清3x/4x"

- **位置**：`app/enhance.py` L32-35（`plan_for` 真人/照片视频固定返回 `("realesr-general-x4v3", 4, 0.5)` = 4 倍模型再缩回 2 倍）；L297 输出文件名 `f"{stem}_高清{self.scale}x.mp4"` 用的是**用户选的倍数**。
- **实测证据**（本次审查模拟实验）：选 3x → 实际输出 2x、文件名标"高清3x"；选 4x → 实际 2x、文件名标"高清4x"。
- **评价**：UI 提示文案（`enhance_tab.py` L278-279"真人/照片模式下视频固定输出 2 倍"）说明固定 2x 是**有意设计**（速度考虑，README 问答也解释了），这个本身没问题；但**文件名与实际内容不一致**是实打实的缺陷，用户拿着"高清4x.mp4"发现分辨率只有 2 倍会认为是 bug。README 功能表格写"真人视频/照片 **2/3/4 倍**"也与此矛盾（照片确实 2/3/4，视频固定 2）。
- **修复思路**：视频路径的输出文件名改用实际输出倍数 `int(scale * eff)`。

### P2-5 半写损坏帧不校验完整性，可能混入成品

- **位置**：`app/enhance.py` L398-399（`missing` 判断只看 `os.path.exists`）。
- **原理**：kill realesrgan 进程的瞬间，它可能正写到某帧 jpg 的一半 → 磁盘上留下**截断的损坏文件**。恢复逻辑只判断"文件存在"即视为已完成，损坏帧直接进入 ffmpeg 合成 → 该帧花屏/绿屏，或整个合成因解码失败而报错（后者反而更安全）。
- **修复思路**：move/判定前做轻量校验（文件大小 > 0 且 jpg 以 FFD9 结尾），损坏帧按缺失重算。

### P2-6 恢复任务中途取消：本轮已算的帧被丢弃重算

- **位置**：`app/enhance.py` L424-425（输出到临时目录 `out_r`）→ L426-428（全部算完才 move 回 `frames_out`）；`except CancelledError` L441-443 只存档不 move。
- **原理**：`EnhanceTask` 首轮直接写 `frames_out`，取消不丢进度；但 `ResumeTask` 把本轮算的帧先放 `out_r`，取消瞬间 `out_r` 里已完成的帧**不会被搬回** `frames_out`，下次恢复 `shutil.rmtree(out_r)` 直接扔掉 → 重算。"已算部分零重复计算"的承诺在恢复→再取消场景不成立（属效率损失，非数据损坏）。
- **修复思路**：`except CancelledError` 分支里先把 `out_r` 已有文件 move 回 `frames_out` 再存档。

### P2-7 批量增强多视频：失败任务的现场档案被后续文件覆盖，成"孤儿"

- **位置**：`app/enhance.py` L239（一个 `EnhanceTask` 顺序处理 `files` 列表）+ L306/L313（每个视频**覆盖写同一个** `.sgjob_{task_id}.json`）。
- **原理**：批量拖入 [A.mp4, B.mp4]，A 增强失败（如 Vulkan 崩溃）→ `mark_job` 标记 interrupted → 循环继续处理 B → `write_job` **覆盖**档案为 B 的信息 → B 成功后 `clear_job` 删档案。结果：A 的 `.sgtmp_*_1` 帧目录永久残留磁盘，且**没有任何档案指向它**——既占空间（可达数 GB）又无法通过"恢复任务"找回。
- **修复思路**：档案文件名带上 idx（`.sgjob_{task_id}_{idx}.json`），或失败后中止整批。

### P2-8 日志滚动机制在 Windows 上必然失效，app.log 无限增长

- **位置**：`app/proc.py` L42-53（`stderr_target` 打开全局单例 `_fh` 后**永不关闭**）+ L30-39（`_rotate` 的 `os.replace` 被 `except OSError: pass` 吞掉）。
- **实测证据**（本次审查模拟实验）：文件被 `"ab"` 句柄持有时执行 `os.replace` → **`PermissionError`（Windows 共享冲突）**。`_fh` 一旦打开，后续所有 `_rotate` 调用（`append_log` 每次都会尝试）必然失败且静默——`app.log` 超过 1MB 后永远不会滚动。
- **影响**：长期使用日志无限增长（子进程 stderr 持续追加）。量级温和（纯文本），但对"报障看日志"的定位是慢性伤害。
- **修复思路**：`append_log` 每次独立开关句柄；或 `os.replace` 前先关 `_fh` 再重开；或用 `FILE_SHARE_DELETE` 打开。

### P2-9 取消任务时 deleteLater 存活的 QThread，存在崩溃风险

- **位置**：`app/download_tab.py` L704-709（`th.wait(2000)` 超时后照常 `deleteLater`）、`enhance_tab.py` L381-389 / `cut_tab.py` L351-355（同样模式，wait 3 秒）。
- **原理**：取消时若工作线程 2~3 秒内没退出（yt-dlp 的取消清理链路可能超 2 秒；直链下载 `resp.read()` 网络卡死时最长阻塞 30 秒），`wait` 超时 → `deleteLater` → 事件循环删除 QThread 对象时线程仍在运行 → Qt 6 触发 `qFatal("QThread: Destroyed while thread is still running")` → **进程 abort 崩溃**。
- **触发条件**：取消 + 线程恰好卡在不可快速中断的等待上。低概率、真实存在、后果是整个应用闪退。
- **修复思路**：`deleteLater` 前用 `isFinished()`/`isRunning()` 判断，未退出就不删除（留给线程自身的 `finished` 信号再清理）；或只置引用为 None 不 deleteLater。

### P2-10 高分辨率真人视频增强的磁盘需求无任何预检

- **原理**：真人视频走"4 倍模型再缩回"路径，**中间帧是 4 倍尺寸的 jpg**（1080p 源 → 8K 中间帧，单帧约 2~5MB）。10 分钟 24fps 视频的中间帧总量可达 **30~70GB**，加上输入帧。默认输出目录在**桌面（C 盘）**。代码全程无磁盘空间估算/预检，写满后 ffmpeg 报 No space（能被 P1-1 的档案机制接住，前提是走异常路径）。
- **修复思路**：抽帧前按 `帧数 × 单帧估算大小` 预检目标盘剩余空间，不足时给出明确提示（提供降帧质/换盘选项更好）。

### P2-11 格式转换是"替换"语义：转换成功即删除原文件

- **位置**：`app/media_convert.py` L48/L64/L75（成功后 `os.remove(src)`）；`app/ytdlp_dl.py` L267-283（音频模式未设 `"keepvideo": True`，yt-dlp 默认删除原视频）。
- **原理**：直链下载 MP4 选格式 MP3 → 下载完整视频 → 提取 mp3 → **删除视频**。UI 文案写的是"下载后提取音频并转为 MP3"，没有明说原视频会消失。想"视频和音频都要"的用户会丢数据（需重新下载）。m4a/图片转换同理。
- **修复思路**：至少在 `save_hint` 文案里写明"将替换原文件"；或提供"保留原文件"开关。
