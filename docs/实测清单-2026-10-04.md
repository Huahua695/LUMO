### 0.2 环境与路径（上一轮踩过的坑，务必照做）

1. **临时目录用 ASCII 路径**，例如 `E:\bench_tmp`。**不要用 `%TEMP%`**：本机 Windows 用户名含全角括号（`Admin（无密码）`），会让 `sed`、部分 Python 字符串处理和某些外部工具解析失败。
2. **不要在 Git Bash 里把 `/tmp/...` 传给 `ffmpeg.exe`**。原生 Windows 程序不认 MSYS 路径，会报 `Could find no file or sequence with pattern`。要么用 Windows 路径，要么用 `pwd -W` 转换。
3. **计时用 Python，不要用 `bc`**（Git Bash 环境无 `bc`）。
4. **中文输出乱码**：Python 一律加 `-X utf8`；控制台 mojibake 不影响测量结果，但会污染报告，建议把结果写文件再读。
5. **ffmpeg 8 的空输出是 `nul` 不是 `-`**：`-f null nul`。写 `-` 会报 `Error opening output files: Invalid argument`。
6. **`-vsync` 在 ffmpeg 8 已被移除**，一律用 `-fps_mode`。
7. **image2 序列输出前必须先建目录**，否则 ffmpeg 静默失败。
8. ⚠️ **`backup_frames/out` 是 3.4 GB 的真实超分帧，是本轮最重要的测试素材。只读，绝对不要删除、移动或写入。** 需要子集时用 `cp` 复制到临时目录。

## 1. 超分引擎（占全流程 95.9%，最高优先级）

### S1 · tile × 分辨率 × 显存占用矩阵 【P0】

**为什么测**：上一轮只测了 tile 对**速度**的影响（`-t 256` +11.7%、`-t 32` -66%），没测**显存**。而"显存感知地选 tile"这个方案能不能成立，完全取决于显存与 tile/分辨率的实际关系。本机 31.4 GB 统一内存在 3840×6864 下 `-t 256` 都没炸，说明**必须量化才能外推到 2 GB 显存的机器**。

**怎么测**：对下列每个 (输入分辨率, `-t`) 组合，记录 ①耗时/帧率 ②GPU 显存峰值 ③系统内存峰值 ④是否失败。

- 输入分辨率：`478×858`、`1280×720`、`1920×1080`、`2560×1440`
- 模型：`realesr-animevideov3`，`-s 2`（先用这一个跑通矩阵，S3 再换模型）
- `-t` 取值：`0`(auto)、`64`、`128`、`256`、`384`、`512`
- 每组 ≥ 16 帧，避免模型加载开销主导

**显存测量方法**（Intel/AMD 无 nvidia-smi，用 Windows 性能计数器）：

```powershell
# 先启动 realesrgan，拿到 PID，再采样该进程的 GPU 内存
Get-Counter '\GPU Process Memory(*pid_<PID>_*)\Dedicated Usage',
            '\GPU Process Memory(*pid_<PID>_*)\Shared Usage' `
  -SampleInterval 1 -MaxSamples 30
```

实例名形如 `pid_12345_luid_0x00000000_...`。取 30 次采样的**最大值**。
若计数器不可用，退而用任务管理器"性能→GPU"的专用 GPU 内存读数人工记录，并在报告注明测量方式。

**判定标准 / 要回答的问题**：
1. 显存峰值与 tile 是线性还是超线性？与分辨率的关系？
2. 能否拟合出一个可用公式（如 `显存 ≈ f(tile, W, H, scale)`）用于运行时估算？
3. **在 2 GB 显存约束下，各分辨率允许的最大 tile 是多少？**（用实测数据反推，不要猜）
4. `-t 0`(auto) 实际选了什么值？（可从速度反推，或用 `-v` 看是否打印）

**报告需含**：完整矩阵表 + 显存曲线 + 反推出的 2 GB 安全 tile 表。

### S2 · 强制 OOM，捕获真实报错文本 【P0】

**为什么测**：既有 **P3-23** 指出显存不足时被误报成"可能显卡驱动不支持 Vulkan"（`enhance.py:206-207`），用户无从缓解。要修就必须知道**引擎 OOM 时到底输出什么**——现在的报错文案是猜的。

**怎么测**：用两种手段逼出 OOM，各自捕获完整 stderr：

1. **超大 tile + 超大分辨率**：`-t 1024`（甚至 2048）配 `3840×2160` 以上输入、`-s 4`
2. **并发挤占显存**：同时启动 4~8 个 realesrgan 进程跑大分辨率，直到有进程失败

```bash
tools/realesrgan/realesrgan-ncnn-vulkan.exe -i <大分辨率输入> -o <out> \
  -n realesr-animevideov3 -s 4 -m tools/realesrgan/models -f jpg -t 1024 2> oom.txt
echo "exit code: $?"
```

**判定标准 / 要回答的问题**：
1. **完整的 stderr 原文**（一字不改地贴进报告，这是修文案的唯一依据）
2. **进程退出码**是多少？（`run_realesrgan` 目前只用 `rc != 0` 笼统报错）
3. OOM 时是否已经写出的帧是完整的？还是留下截断帧？（关系到 `_frame_ok` 的 JPEG `FFD9` 校验是否够用）
4. 失败是"立即失败"还是"跑很久才失败"？（决定回退重试的时间成本）
5. 同一 tile 减半后重跑是否必然成功？（验证"自动减半重试"策略可行）

**若本机显存太大怎么也逼不出 OOM**：明确在报告里写"本机无法复现"，并给出尝试过的最大配置。**不要编造报错文本。**

### S3 · `-j` / `-t` 在其余三个模型上重测 【P1】

**为什么测**：上一轮只测了 `realesr-animevideov3`（最轻的视频模型）。**真人路径用的是 `realesr-general-x4v3`，内部按 4x 计算再缩回，显存和算力特征完全不同**；照片模式的 `realesrgan-x4plus`（31.9 MB，最重）也从没测过。animevideov3 的最优 tile 不一定适用于它们。

**怎么测**：对下列模型各跑一组 `-t` ∈ {auto, 128, 256, 384} × `-j` ∈ {默认, `1:4:2`}，输入 `1280×720`，≥16 帧：

| 模型 | 对应模式 | `-s` |
|---|---|---|
| `realesr-general-x4v3` | 真人·通用（图片 + 视频） | 4 |
| `realesrgan-x4plus` | 照片模式 | 4 |
| `realesrgan-x4plus-anime` | 动漫图片 | 4 |

**判定标准**：
1. 各模型的最优 `-t` 是否一致？若不一致，方案必须**按模型分别配表**，不能用一个全局值。
2. `general-x4v3 -s 4` 的实测帧率是多少？（README 说真人视频固定 2x 是"速度考虑"，需要一个真实数字来验证这个取舍是否还成立）
3. 重模型的显存峰值是否显著高于 animevideov3？（关系到 S1 的公式要不要带模型维度）

### S4 · 长任务帧率 + 模型加载时间 【P1】

**为什么测**：上一轮单次只跑 24 帧，模型加载开销（估 1~2 s，**未实测**）占比偏高，导致绝对帧率偏悲观（2.23 f/s）。报告里的时间预算需要用长任务数字重算。

**怎么测**：
1. 单独测模型加载：`-i` 只放 **1 帧**，总耗时减去单帧推理时间 ≈ 加载时间。或直接对 1/8/24/64 帧各跑一次，用线性拟合求截距。
2. 长任务：≥300 帧，`realesr-animevideov3 -s 2 -t 256`，记录稳态帧率。

**判定标准**：
1. 模型加载时间实测值（秒），以及是否随模型大小变化。
2. 稳态帧率 vs 上一轮的 2.23 f/s，差多少？据此**修正报告 §一 的时间预算表**。
3. 长任务中帧率是否衰减（显存碎片/温度降频）？记录前 100 帧与后 100 帧的分段帧率。

### S5 · 大目录下的续跑硬链接 【P2】

**为什么测**：`ResumeTask`（`enhance.py:461-491`）恢复时要 `os.listdir(frames_in)` + 对每帧 `_frame_ok()`（打开文件读末尾 2 字节）+ `os.link()`。4488 帧时是 4488 次 open+seek+read。这个开销没测过。

**怎么测**：造一个含 4488 个 JPEG 的目录，测量 ①`os.listdir` ②逐帧 `_frame_ok` ③逐帧 `os.link` 各自的耗时。再测 18000 帧（可用 `backup_frames/out` 的文件名列表复制生成，**不要动原目录**）。

**判定标准**：恢复前的"扫描+硬链接"阶段耗时占整个续跑的比例。若 4488 帧要 10 秒以上，则续跑体验有可感知延迟，方案里要考虑加进度提示或缓存校验结果。

## 2. 合成与剪切

### C1 · `veryfast` vs `medium` 在 4K/8K 下重测 【P1】

**为什么测**：上一轮的 `veryfast` 结论（+39.6% 吞吐、SSIM 仅降 0.00042、体积小 8%）只在 **956×1716** 上测过。而**真人视频路径的中间帧是 4 倍尺寸**（1080p 源 → 4320p 中间帧，见 P2-10），分辨率提高 8 倍后 preset 的收益比例可能完全不同。

**怎么测**：在 `3840×2160` 和（若磁盘允许）`5120×2880` 的真实超分帧上，各测 `libx264 crf16` 的 `medium` / `veryfast` / `ultrafast`，各跑 3 次取均值，记录耗时、体积、SSIM。

素材：把 `backup_frames/out` 的帧用 lanczos 放大到目标分辨率后作为输入（模拟真人路径的中间帧）。

**判定标准**：
1. 4K 下 veryfast 的提速比例是否仍 ≥30%？
2. SSIM 差值是否仍 <0.001？
3. "veryfast 体积更小"这个反常现象在 4K 下是否复现？（若不复现，说明是小样本特性，方案文案要改）

---

### C2 · 剪切路径的硬件编码 【P0，且与上一轮结论相反的可能性最高】

**为什么测（重要）**：上一轮否决硬件编码的依据是"**合成链的地板在 JPEG 解码 113.8 f/s，编码器不是瓶颈**"。但这个依据**只适用于增强页的合成步骤**（输入是 JPEG 序列）。

**剪切路径的瓶颈结构完全不同**：`cut_engine.py:130-136` 的精确剪切是 `视频 → 解码 H.264 → 编码 H.264`，**没有 JPEG 这个地板**，而且解码和编码都可以走 GPU（`-hwaccel qsv` + `-c:v h264_qsv` 全程零拷贝）。**所以硬件编码在剪切路径上很可能真的有效——上一轮的否决不适用于这里，必须单独测。**

**怎么测**：用一段真实视频（≥1080p、≥30 秒、H.264），测精确剪切的全程耗时：

| 配置 | 命令要点 |
|---|---|
| 当前实现 | `-c:v libx264 -crf 17 -preset medium` |
| CPU 快档 | `-c:v libx264 -crf 17 -preset veryfast` |
| QSV 软解硬编 | `-c:v h264_qsv -global_quality 19` |
| QSV 全硬件 | `-hwaccel qsv -c:v h264_qsv -global_quality 19` |
| QSV + veryfast 等价档 | `-hwaccel qsv -c:v h264_qsv -preset veryfast -global_quality 19` |

各测 3 次，记录耗时、输出体积、SSIM（以源视频为参考）。

**判定标准**：
1. 剪切路径的地板在哪？（先测 `-c:v copy` 和 `-f null` 两个基准）
2. QSV 全硬件相对当前实现提速多少倍？
3. **质量代价**：同 SSIM 下 QSV 需要多大的 `-global_quality`？体积膨胀多少？
4. 若提速 ≥2 倍且质量可控 → 剪切路径应改用硬件编码（与增强路径结论相反，需在报告中明确写出这个对比）。

### C3 · 空转 lanczos 在 4K 下重测 【P2】

**为什么测**：上一轮实测 `eff==1.0` 时 `assemble()` 仍跑一遍 lanczos 只慢 1.4%（噪声级），因此判为"不值得改"。但那是在 956×1716 上测的，4K/8K 下 lanczos 的绝对成本更高，比例可能变化。

**怎么测**：4K 帧序列上对比"带 `-vf scale=trunc(iw*1.0/2)*2:...:flags=lanczos`"与"完全不带 `-vf`"的编码耗时，各 3 次。

**判定标准**：差值 >5% 才值得改；≤5% 维持上一轮结论。

## 3. VFR 与抽帧

### V1 · CFR 源改用 `-fps_mode passthrough` 的回归验证 【P0】

**为什么测**：这是 §3.3 方案**最大的风险点**。把 `extract_frames` 的 `-r {fps}` 换成 `-fps_mode passthrough` 后，**必须保证恒定帧率（CFR）源的行为完全不变**——否则会为修 VFR 而弄坏占绝大多数的 CFR 场景。

**怎么测**：准备 ≥5 个 CFR 源（不同帧率：23.976 / 24 / 25 / 29.97 / 30 / 60，含非整数帧率），对每个源分别用两种方式抽帧：

```bash
# 当前
tools/ffmpeg.exe -y -i src.mp4 -r <fps> -qscale:v 1 out/%06d.jpg
# 建议
tools/ffmpeg.exe -y -i src.mp4 -fps_mode passthrough -qscale:v 1 out/%06d.jpg
```

**判定标准（必须逐项给出数字）**：
1. 两种方式抽出的**帧数是否完全一致**？逐个源列出。
2. 帧内容是否一致？（对同名帧做 MD5 或 SSIM 比对，抽查首/中/尾各 3 帧）
3. 非整数帧率（23.976 / 29.97）下，`probe_fps` 取 `r_frame_rate` 与 `avg_frame_rate` 的值分别是多少？两者是否相等？若不等，`assemble` 用哪个 `-framerate` 才能保持时长正确？
4. **合成回验证**：抽出的帧用 `-framerate <fps>` 合成后，成品时长与源视频时长差多少毫秒？音频是否与视频等长？

**只要有任一 CFR 源出现帧数不一致或时长漂移，§3.3 方案就不能按原样实施**，必须在报告里标红。

---

### V2 · 真实片源的 VFR 普查 【P1】

**为什么测**：上一轮的 VFR 结论（160 帧 → 240 帧，虚增 50%）建立在**用 `testsrc2` 拼出来的合成 VFR 视频**上。真实世界片源的 VFR 特征可能完全不同，而"这个优化值不值得做、能覆盖多少用户场景"取决于此。

**怎么测**：用本工具**实际下载**下列各类片源各 ≥2 个，逐个 `ffprobe` 记录：

| 片源类型 | 采集方式 |
|---|---|
| B 站（普通/高清） | 下载页 |
| 抖音无水印 | 下载页 |
| YouTube（需代理） | 下载页，若无代理则标注"未采集" |
| 手机录屏（iPhone / Android） | 需外部提供样本，若无则标注"未采集" |
| OBS / 游戏录制 | 同上 |
| m3u8 下载的视频 | 下载页 |

每个样本记录：
```
r_frame_rate / avg_frame_rate / nb_frames / duration / codec / 分辨率
两者比值 = r ÷ avg   ← 关键指标，决定帧数虚增倍数
是否 VFR（比值 ≠ 1.0 即为 VFR）
```

**判定标准**：
1. 各来源的 VFR 占比是多少？
2. 虚增倍数的分布（最坏情况是多少倍）？
3. **据此给出结论：VFR 修复的实际覆盖面是"极少数场景"还是"常见场景"**。这直接决定 §3.3 的优先级该排第几。

**若因网络/代理/Cookie 限制无法采集某类片源，如实标注"未采集"，不要用合成样本代替。**

---

### V3 · VFR 源的时长漂移与音画同步量化 【P1】

**为什么测**：`审计报告.md` 第八节把 VFR 描述为"可能有**轻微**音画偏移"。上一轮合成样本测出 +1.7% 漂移（10 分钟视频约 10 秒），说明"轻微"这个措辞可能不准。需要真实片源的数据来定论。

**怎么测**：对 V2 中识别为 VFR 的样本，走完整增强流程（可用小倍数、截短片段以省时间），然后：
1. 对比成品与源的 `duration`
2. 用 `ffprobe` 分别取成品视频流与音频流的 duration，计算差值
3. 主观检查末尾是否音画错位（记录偏移秒数）

**判定标准**：给出"每分钟源视频累积多少毫秒偏移"的实测系数。若 ≥50 ms/min，则 `审计报告.md` 的"轻微"措辞需要修订，且 UI 应给出提示。

## 4. 进度上报机制

### P1 · 大目录 `scandir` 的实际开销 【P1】

**为什么测**：`enhance.py:194-199` 每 0.6 秒对整个输出目录调一次 `_count_frames()`（`os.scandir` 全量计数）。上一轮**断言**这在 18000 帧时是问题，但**没有实测**。要决定是改自适应间隔、还是改读 stderr，得先知道它到底多贵。

**怎么测**：造 1000 / 4488 / 18000 / 50000 个 JPEG 的目录，各测 `os.scandir` 全量计数 100 次的平均耗时。同时测"边有进程在往该目录写文件、边 scandir"的耗时（模拟真实争抢）。

**判定标准**：
1. 各规模下单次 scandir 耗时（ms）
2. 占 0.6 s 轮询周期的百分比
3. 有并发写入时是否显著变慢
4. **结论**：若 18000 帧时单次 <20 ms 且无争抢恶化，则这条只是"不优雅"而非"性能问题"，方案应降级；若 >100 ms，则值得改。

### P2 · realesrgan stderr 进度格式的稳定性 【P2】

**为什么测**：上一轮发现引擎**本身就在 stderr 打印百分比**（`0.00%`、`6.67%`…，`\r` 分隔），这是替代 scandir 的现成数据源。但只在 animevideov3 + 24 帧 + 默认 `-j` 下观察过一次，格式稳定性未知。**要改成解析 stderr，必须先确认格式不会随配置变化。**

**怎么测**：在下列各组合下抓取完整 stderr，记录进度行的出现规律：

- 模型：animevideov3 / general-x4v3 / x4plus
- 帧数：1 / 15 / 24 / 150 / 1000
- `-j`：默认 / `1:4:2`
- 是否加 `-v`

**判定标准**：
1. 进度更新的**次数**与帧数是什么关系？（上一轮 24 帧出现 15 次更新，即 6.67% 步进 —— 是固定 15 段，还是与 `-j` 的 proc 线程数相关？）
2. 是否总是以 `NN.NN%` 格式？有无其它形态（如带前缀、带帧号）？
3. 分隔符是 `\r` 还是 `\n`？末尾是否有换行？
4. stderr 里除进度外还有哪些内容（GPU 初始化日志的完整格式）？解析时需要过滤什么？
5. **风险确认**：若进度只在任务结束时才批量刷出，则无法用于实时进度，方案作废。必须确认它是**边跑边输出**的。

## 5. 体积与打包

### B1 · `avdevice-63.dll` 可删性 【P0】

**为什么测**：3.5 MB。项目不做摄像头/录屏采集，理论上不需要，但 `ffmpeg.exe` 可能静态链接了它。

**怎么测**：**复制一份 dist 到临时目录**（绝不要在原 dist 上操作），在副本里删掉 `tools/avdevice-63.dll`，然后逐个验证：

```bash
ffmpeg.exe -version
ffmpeg.exe -encoders | head
ffprobe.exe -version
# 实际跑一次抽帧 + 合成 + 精确剪切 + 音频提取
```

**判定标准**：删掉后 4 项功能是否全部正常？若 `ffmpeg.exe` 直接启动失败，则**不可删**，报告里写明并放弃这 3.5 MB。

**同时检查**：`tools/` 下是否还有其它未被引用的 DLL（对照 `ffmpeg.exe` 实际加载的模块列表；可用 Process Explorer 或 PowerShell 在 ffmpeg 运行时查其已加载模块）。

### B2 · `PySide6.QtNetwork` 可排除性 【P1】

**为什么测**：全仓检索 `app/` 无任何 `QtNetwork` 导入（yt-dlp 走 Python 的 urllib/ssl）。若能在 spec 的 `excludes` 里排除它，有望连带去掉 `Qt6Network.dll`（1.7 MB）+ Qt 那套 OpenSSL（`libcrypto-3-x64` 5.5 MB + `libssl-3-x64` 1.0 MB）≈ **8 MB**。

**怎么测**：
1. 复制 spec 到临时目录，加 `excludes=[..., 'PySide6.QtNetwork']`，重新打包到临时输出目录
2. 对比 `_internal` 体积变化，确认 `Qt6Network.dll` 和 `libcrypto-3-x64.dll` / `libssl-3-x64.dll` 是否真的消失
3. **完整 GUI 冒烟测试**：启动应用，逐页走一遍——下载（含一个真实 HTTPS 下载）、增强（图片 + 视频各一次）、剪切（**含视频预览播放**，这是 QtMultimedia 路径，最可能依赖 QtNetwork）、设置（改路径并保存）、暗色模式切换、关闭并重启验证"恢复任务"横幅

**判定标准**：
1. 实际省下多少 MB？
2. GUI 冒烟是否全部通过？**任何一项异常就判定为不可排除**，报告写明是哪一步失败的。
3. 特别注意：Qt Multimedia 的媒体后端是否会间接拉起 QtNetwork。

**风险提示**：这条会改打包配置。执行时**只在临时副本上改**，不要提交仓库里的 `拾光工具箱.spec`。

---

### B3 · 两套 OpenSSL 的实际加载方 【P1】

**为什么测**：`_internal/` 里同时存在 `libcrypto-3-x64.dll`(5.5 MB) + `libssl-3-x64.dll`(1.0 MB) 和 `libcrypto-3.dll`(5.0 MB) + `libssl-3.dll`(0.76 MB)，**MD5 不同，是两套不同构建**，合计 12.3 MB。上一轮**推断** `-x64` 那套属于 Qt Network、无后缀那套属于 Python `_ssl.pyd`，但**未验证**。

**怎么测**：
1. 静态：检查 `_internal/*.pyd` 与 `PySide6/*.dll` 各自的导入表（Python 可用 `pefile`，若未安装则 `pip install pefile` 到 venv；或用 PowerShell + `dumpbin` 替代方案）
2. 运行时：启动应用并执行一次 HTTPS 下载，用 Process Explorer 查看进程实际加载了哪些模块（或 PowerShell 枚举进程模块列表）
3. 分别确认 `_ssl.pyd` / `_hashlib.pyd` 链接的是哪个文件名

**判定标准**：
1. 两套各自的归属是否与推断一致？
2. 是否**真的**两套都被加载？若某一套从未被加载，它就是纯冗余，可直接排除。
3. 与 B2 的关系：排除 QtNetwork 后 `-x64` 那套是否自动消失？（B2 的步骤 2 已可回答，交叉验证）

---

### B4 · LZMA vs deflate 压缩率 【P0】

**为什么测**：上一轮发现**仓库里没有任何生成 release zip 的代码**（全仓无 `zipfile` / `make_archive` / `ZipFile` 引用），但 README 指引用户从 Releases 下 zip → 当前发行包是手工压的、不可复现。建议改用 LZMA，但**收益没测过**。

**怎么测**：对 `dist/拾光工具箱/` 整个目录，分别用下列方式压缩并记录耗时与成品体积：

| 方式 | 命令/方法 |
|---|---|
| zip deflate（当前推测做法） | `zipfile.ZIP_DEFLATED`，compresslevel 6 与 9 各测 |
| **zip LZMA** | `zipfile.ZIP_LZMA` |
| zip bzip2 | `zipfile.ZIP_BZIP2`（对照） |
| 7z（若系统装了） | `7z a -mx=9` |

**判定标准**：
1. 各方式的**成品体积**（MB）与**相对 333.5 MB 的压缩率**
2. 各方式的**压缩耗时**（LZMA 可能很慢，要评估是否影响发版流程）
3. **解压后能否正常运行**——这是硬门槛。LZMA 压缩的 zip 需要 Windows 11 或 7-Zip 才能解压；**Windows 10 内置资源管理器不支持 ZIP_LZMA**。必须实测并明确写出兼容性结论。
4. 若 ZIP_LZMA 有兼容性问题，改测"7z 格式发布"或"deflate level 9"的可行性。

⚠️ **这条的结论可能推翻原建议**。README 明确写着支持 Windows 10，如果 ZIP_LZMA 在 Win10 资源管理器下解不开，就不能用，必须换方案。请如实报告。

---

### B5 · spec 参数调整的影响 【P2】

**为什么测**：`spec` 里 `upx=True` 但本机未装 UPX（**实际从未生效**，属误导性配置）；`optimize=0` 可改 `2`。

**怎么测**：
1. 把 `upx` 改 `False`、`optimize` 改 `2`（**在临时副本 spec 上改**），重新打包
2. 对比：`_internal` 体积、exe 体积、PYZ 体积
3. 对比应用**启动时间**（见 B6）与功能是否正常

**判定标准**：`optimize=2` 省下多少？有无副作用（去 docstring 可能影响依赖 `__doc__` 的代码——需检查 `app/` 是否有此类用法）？

**同时确认**：`upx=True` 改为 `False` 后产物是否与当前一致（应当一致，因为本来就没生效）。

### B6 · 应用启动时间与常驻内存 【P2】

**为什么测**：轻量化的用户感知维度之一，从未测过。

**怎么测**：

### B7 · ffmpeg master 构建的风险面 【P2，可跳过】

**为什么测**：捆绑的是 `N-125953-gd3ad8a7fee-20260803`，**master 每日构建而非 release**。已实测到 `-vsync` 这类**选项被直接移除**的破坏性变更。

**怎么测**：把代码里用到的**所有** ffmpeg/ffprobe 参数逐个验证在当前构建下有效：

-ss -i -vn -map 0:a:0? -c:a libmp3lame -q:a 0 -c:a copy -c:a aac -b:a 192k

**判定标准**：有无任何参数触发 deprecation 警告或已失效？`-map 0:s?` 在字幕流缺失时的行为是否正常？

**注**：不建议本轮更换 ffmpeg 构建——LGPL 精简版**不含 libx264**（GPL），会直接破坏合成与精确剪切。若报告里要提减体积，必须先确认这一点。

## 6. 端到端

### E2E1 · 一次完整视频增强的资源分解 【P2】

**为什么测**：上一轮的时间预算表是**分阶段单独测**再相加的，没有端到端验证过。阶段之间可能有重叠开销（磁盘争抢、缓存失效）。

**怎么测**：用一个真实视频（≥3 分钟，720p 或 1080p）走完整动漫增强流程，记录：
1. 三阶段各自的墙钟时间（从应用日志或外部计时）
2. **峰值磁盘占用**（对输出目录定时采样 `du`）
3. **峰值内存**（系统 + GPU）
4. 成品体积、时长、与源的音画同步情况

**判定标准**：分阶段相加 vs 端到端实测的差值。若差 >10%，说明存在未识别的开销，需追查。

---

### E2E2 · 真人路径的磁盘峰值（验证 P2-10 的 30~70 GB 估算） 【P2】

**为什么测**：`审查日志` P2-10 估算真人视频（1080p 源 → 4x 中间帧 → 8K）的中间帧总量为 **30~70 GB**，但那是**推算，未实测**。这个数字直接决定"磁盘预检"功能该按什么公式估算。

**怎么测**：取一段**短的** 1080p 视频（**30 秒以内**，避免真的写满磁盘！），走真人·通用模式增强，记录：
1. 输入帧目录 `frames_in` 的实测大小与单帧大小
2. 输出帧目录 `frames_out` 的实测大小与单帧大小
3. 据此**线性外推**到 10 分钟视频的总量

⚠️ **务必用短视频**。按 P2-10 的估算，10 分钟视频可能写 30~70 GB，有写满系统盘的风险。测前先确认剩余空间，测中监控，测后立即清理。

**判定标准**：给出"每帧字节数 × 帧数"的实测系数，供磁盘预检公式使用。验证 30~70 GB 这个区间是否准确。
