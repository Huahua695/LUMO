## 1. 复核结论

### 1.1 复核通过的部分

| 项 | 报告结论 | 我的复核 | 判定 |
|---|---|---|---|
| **V3** passthrough 陷阱 | passthrough + `r_frame_rate` → 成品塌缩 | 同一素材：成品 **1.792s**（源 7.833s），A/V 差 **-6038ms**；配 `avg_frame_rate` → **7.833s**，A/V 差 **+4ms** | ✅ **完全一致** |
| **V3** 帧数虚增 | 949 vs 215 帧 | `-r 120` → **949 帧**；passthrough → **215 帧**（= 容器 nb_frames） | ✅ 一致 |
| **S1** t512 最优 | +8.7~11.3% vs auto | 478×858 × 2 次重复：auto 2.37 f/s、t256 2.47、t384 2.47、**t512 2.63**（**+11.0%**），方差 ±0.01s | ✅ 一致 |
| **C2** QSV 剪切提速 | 3.06 倍 | libx264 medium 6.646s → QSV 软解硬编 2.480s = **2.64~2.73 倍** | ✅ 量级一致（差异来自机器状态） |

### 1.2 需要修正报告的一处因果关系 ⚠️

报告 C2 的结论是：**"`-hwaccel qsv` 全硬件形态在本构建上不可用……若采用 QSV，必须用软解硬编形态"**。

**这个因果判断不成立。** 我逐参数隔离测试后，破坏者只有一个：`-pix_fmt yuv420p`。

| 变体（均为 `-hwaccel qsv -hwaccel_output_format qsv` + `-c:v h264_qsv`） | 结果 |
|---|---|
| A 仅 `-map 0:v:0 -an`，无 pix_fmt | ✅ 2.117s |
| **B 加 `-pix_fmt yuv420p`** | ❌ `Impossible to convert between the formats supported by the filter 'Parsed_null_0'` |
| C 加 `-map 0:a? -c:a copy` | ✅ 1.951s |
| D 再加 `-map 0:s?` | ✅ 1.895s |
| E 再加 `+faststart` | ✅ 1.927s |
| **F 全套（含 pix_fmt，即真实代码形态）** | ❌ 同 B |

**结论**：`-pix_fmt yuv420p` 会插入一个软件格式转换滤镜，而它无法处理 qsv 硬件帧 → 报错。去掉它之后全硬件路径**可用，而且是最快的**：

```
当前 libx264 medium      6.646s   输出 pix_fmt = yuvj420p
QSV 软解硬编（报告方案）  2.480s   输出 pix_fmt = yuvj420p
QSV 全硬件（去掉pix_fmt） 2.435s   输出 pix_fmt = yuvj420p  ← 与当前实现完全一致
源视频                             pix_fmt = yuvj420p
```

**输出像素格式与当前实现逐字相同，无兼容性回退。**

### 1.3 复核中带出的、比报告更重要的一个判断

把三个方案的提速放在一起看（同一段 25 秒 1080×1920 剪切）：

| 方案 | 耗时 | 相对当前 | 依赖 |
|---|---|---|---|
| 当前 libx264 medium | 6.646s | 1.00× | — |
| **libx264 veryfast** | **2.680s** | **2.48×** | **无（纯 CPU，全平台一致）** |
| QSV 软解硬编 gq19 | 2.480s | 2.68× | Intel 显卡 + 驱动 |
| QSV 全硬件 | 2.435s | 2.73× | Intel 显卡 + 驱动 |

**`veryfast` 一个词就拿到了 2.48×，QSV 再往上只有 10%（2.48→2.73）。**

而这 10% 的代价是：显卡厂商探测、驱动兼容性判断、失败回退链，以及——按报告 §4 明确列出的——**`h264_nvenc` / `h264_amf` 在本机完全未测**。项目宣称"Intel / AMD / NVIDIA 显卡通吃"，若只实现 QSV，等于给 2/3 的用户上了一段从未验证过的代码路径，而收益只有 10%。

**因此本方案把 QSV 从报告的第 1 位降到"待定"（§4 C4），把 `veryfast` 提到第 1 位。** 这是本文与报告 §6 优先级表最大的分歧，理由如上。

## 2. 批次 A：一行级改动，先做（零风险 / 已实测）

四项互不依赖，可一次性提交。**全部有实测数据支撑，无需再测。**

### A1 · 合成 preset：`medium` → `veryfast`

- **位置**：`app/enhance.py:247`
- **改动**：`"-preset", "medium"` → `"-preset", "veryfast"`
- **实测收益**：
  - 956×1716：78.6 → 109.7 f/s（**+39.6%**）
  - 3840×2160：14.4 → 36.8 f/s（**+155%**）
  - 5120×2880：7.6 → 19.8 f/s（**+159%**）
  - **规律：分辨率越高收益越大**（C1）。真人路径的中间帧是 4K~8K 级，正是收益最大处。
- **质量**：SSIM 差 0.00040~0.00053（肉眼不可辨）；**输出体积反而小 1.3~1.9%**（三个分辨率均复现，非噪声）
- **风险**：极低。3 次重复方差 ±0.02s
- **注意**：`ultrafast` 不要用——速度快 1.9× 但体积 **+82%**、SSIM 再降 0.0013

### A2 · 剪切 preset：`medium` → `veryfast`

- **位置**：`app/cut_engine.py:134`（精确剪切分支）
- **改动**：同 A1
- **实测收益**：25 秒 1080p 剪切 **6.646s → 2.680s（2.48×）**，体积 27.35 → 25.65MB
- **风险**：极低；无损剪切分支（`cut_engine.py:138`）不涉及编码，不动
- **注意**：`-map 0:s?` 字幕流与 `-c:a copy` 均不受 preset 影响

### A3 · 超分 tile：按模型配表

- **位置**：`app/enhance.py:185-186`（`run_realesrgan` 的 `cmd` 构造）
- **改动**：按模型追加 `-t`，**不要动 `-j`**（报告 S3：`-j` 在全部四个模型上差异都在噪声内，上一轮测得的 +7.6% 未能复现 → 整个维度砍掉）

| 模型 | 建议 `-t` | 实测收益 | 显存峰值 | 依据 |
|---|---|---|---|---|
| `realesr-animevideov3` | **512** | **+11.0%**（我复核值） | 320 MB | S1：4 个分辨率下 t512 全部最快 |
| `realesr-general-x4v3` | **384** | +6.9% | 219 MB | S3 |
| `realesrgan-x4plus` | **不改，留 auto** | （t256 仅 +5.5%） | auto 1242 MB / t256 **1820 MB** | S3 |
| `realesrgan-x4plus-anime` | **不改，留 auto** | （t256 仅 +7.2%） | auto 1081 MB / t256 **1658 MB** | S3 |

**为什么两个重模型不动**：它们的 auto 档就已经吃 1.1~1.2 GB，调到 t256 会到 1.7~1.8 GB。**用 5~7% 的提速换掉 2 GB 显存机器上的可用性，不划算。** 报告 S3 自己也得出同样结论（"照片模式在低配机上应当默认 auto 或更小 tile"）。轻模型（320 MB / 219 MB）即使在 2 GB 卡上也留有余量，所以可以放心调大。

- **总收益**：4488 帧动漫任务 **33.5 → 28.2 min，省 5.3 min（-16%）**（S4 修正后的时间预算）
- **实现形态**：一个 `dict` 常量 + `cmd` 里条件追加，约 8 行
- **风险**：低。**不要实现"OOM 自动减半重试"**——见 §4 C3

### A4 · 打包参数：`upx=False` + `optimize=2`

- **位置**：**`scripts/build_app.py:18-37` 的 `build_exe()` 命令列表**，⚠️ **不是 `拾光工具箱.spec`**
- **原因**：`build_app.py` 用命令行参数调 PyInstaller 并 `--specpath ROOT` 生成 spec——**仓库里的 `.spec` 是构建产物，不是配置源头**。改 spec 会在下次构建时被覆盖。
- **改动**：命令列表加 `"--noupx"`、`"--optimize", "2"`
- **实测收益**：exe 9.94 → **9.26 MB（-0.68MB）**，`--selftest` rc=0（B5）
- **`upx=True → False`**：产物逐项一致（本机从未装 UPX，一直在静默跳过）。改了只是让配置与实际行为一致，消除误导。
- **副作用检查**：B5 已确认全仓无依赖 `__doc__` 的代码。**但 yt_dlp 等第三方库同样会被 optimize=2 处理，正式实施后必须完整跑一遍 `tests/test_suite.py`**（当前 33 项）。

**批次 A 合计**：动漫增强 4488 帧任务省约 **5.5 分钟**；剪切快 **2.5 倍**；包体 -0.68MB；**代码改动约 12 行**。

## 3. 批次 B：需要设计的改动

### B1 · VFR 修复（**必须成对上线，否则会造成严重回归**）

这是本轮最重要的正确性修复，也是唯一能带来"数量级"收益的一项——但**只对有 VFR 源的用户**。

- **位置**：`app/enhance.py:211-227`（`probe_fps`）、`enhance.py:230-237`（`extract_frames`）、`enhance.py:240-249`（`assemble`）
- **实测依据**：
  - V1：6 个 CFR 源（含 23.976 / 29.97）改用 passthrough 后**帧数逐一相等、2893 帧逐帧 MD5 全同、成品时长漂移 0ms** → **CFR 侧零风险**
  - V3：真 VFR 源（Game Bar 录屏，r=120 / avg=27.45）当前抽出 **949 帧而非 215 帧（虚增 4.4 倍）**，音频比视频短 79ms
  - V2：B站×3 + m3u8 全是 CFR；**屏幕录制类才是 VFR 重灾区**

**⚠️ 硬性约束（我已独立复核）**：`-fps_mode passthrough` **必须**与 `avg_frame_rate` 配套。若只改抽帧、`assemble` 仍用 `r_frame_rate`：

```
成品时长 7.833s → 1.792s   （塌缩 77%）
A/V 差   +4ms   → -6038ms  （音画差 6 秒）
```

**比现状糟糕得多。** 这两处必须在同一次提交里改完，不可分批。

**设计**：

1. `probe_fps` 改为**优先取 `avg_frame_rate`**，缺失或非法（`0/0`、超出 1~240）时回退 `r_frame_rate`。保留现有的 `1 <= fps <= 240` 合法性校验。
2. `extract_frames` 的 `-r {fps}` 改为 `-fps_mode passthrough`。
   ⚠️ 不要用 `-vsync`——ffmpeg 8 已**移除**该选项（第一轮实测：`Unrecognized option 'vsync'`）。
3. **加一道自校正**：抽帧完成后用 `实际帧数 ÷ 源时长` 反算 fps，若与 `avg_frame_rate` 偏差 >2%，以反算值为准。理由：V3 已观察到容器 duration(7.900s) 与视频流净时长(7.833s) 存在 67ms 的容器级 padding，`avg_frame_rate` 不一定总是最准。**这是报告未覆盖的加固点。**
4. **任务档案兼容**：`.sgjob_*.json` 里的 `fps` 字段语义变了（旧档案存的是 `r_frame_rate`）。老档案在新逻辑下恢复会错。处理方式二选一：
   - 档案加 `"ver": 2`，读到 `ver` 缺失或为 1 的档案时**放弃续跑并提示用户重新开始**（简单、安全）；
   - 或恢复时用源视频重新 probe 一次 fps 覆盖档案值（更友好，但要处理源文件已变的场景）。
   **建议前者**——续跑是低频路径，不值得为它引入不确定性。
5. **回归测试**：把 V1 的 6 个 CFR 源 + V3 的 VFR 源固化进 `tests/test_suite.py`（帧数断言 + 成品时长断言 + A/V 差断言）。

- **收益**：VFR 源超分帧数 **-77%**（949→215），即录屏用户的增强耗时降到约 1/4.4；A/V 差 79ms → 4ms
- **风险**：**中**。CFR 侧已由 V1 证明安全，风险集中在档案兼容与 `avg_frame_rate` 异常的片源。
- **优先级判断**：V2 显示主路径（下载点播视频）几乎全是 CFR。**所以这不是"全体用户的分钟级收益"，而是"录屏用户的数量级收益"。** 若你的用户主要是下载增强，可排在 B2 之后；若你自己常拿录屏做增强，应提前。

### B2 · 真人路径的磁盘 + 耗时预检（我认为这是当前最严重的可用性问题）

- **位置**：`app/enhance.py:330-351`（`_video` 开头）+ `app/enhance_tab.py`（提示 UI）
- **实测依据（E2E2，8 秒 1080×1920 真人·通用流程全程实测）**：

| 指标 | 实测值 |
|---|---|
| 中间帧单帧大小（7680×4320 JPEG） | **9.8 MB** |
| 超分速度 | **4.32 s/帧**（0.23 f/s） |
| 195 帧输出目录峰值 | 1.9 GB |
| **外推 10 分钟 1080p@24fps（14400 帧）中间帧** | **≈ 139.7 GB** |
| **外推同任务耗时** | **≈ 17.3 小时** |

- **`审查日志` P2-10 的 30~70 GB 估算低估了 2~4.7 倍。** 而且 P2-10 只提了磁盘、**完全没提时间**——17 小时这个数字比磁盘满更劝退。
- **预检公式**（用 E2E2 的实测系数）：
  ```
  帧数     = fps × 时长(s)
  单帧字节 ≈ 10 MB × (源宽×源高 / 2.07 Mpx)      # 2.07Mpx = 1080×1920，E2E2 基准
  中间帧总量 ≈ 帧数 × 单帧字节 × 安全系数 1.15
  预计耗时  ≈ 帧数 × 单帧秒数（按模型/分辨率查表，见 S3/S4/E2E2）
  ```
- **行为设计**（遵循「简洁」原则，不新增对话框）：
  - 磁盘不足 → **阻止启动**，在现有任务行位置直接给出"需要约 X GB，目标盘仅剩 Y GB"
  - 预计耗时 > 1 小时 → **不阻止**，但在启动前于同一位置显示一行"预计约 N 小时 · 中间文件约 M GB"，让用户自己决定
  - 不加新控件、不加新页面，复用现有任务行的 hint 区域
- **关联**：与 §3.5（不持久化 `frames_in`）互补——E2E2 实测输入帧只占 2.6GB（10 分钟外推），删掉它能省约 2%，**优先级远低于本项**，可并入本批一起做。

### B3 · 把 release zip 步骤写进 `build_app.py`

- **位置**：`scripts/build_app.py`（新增一步，接在 `make_shortcut()` 之后）
- **现状**：**全仓无任何生成 zip 的代码**（无 `zipfile` / `make_archive` / `ZipFile` 引用），但 README 指引用户从 Releases 下 `拾光工具箱-vX.Y.Z.zip` → **当前发行包是手工压的，不可复现**。这本身是个流程缺陷，与压缩算法无关。
- **压缩算法：建议本轮先用 deflate L6，不要用 LZMA。**
  - 实测（B4）：LZMA **136.3MB** vs deflate L6 **163.6MB**（-27.3MB / -17%），压缩耗时 116s vs 13s
  - **但 Win10 资源管理器双击解压 LZMA 的行为未实测**（执行机是 Win11）。报告已验证 Win11 的 bsdtar 与 `Expand-Archive` 都能解，但**资源管理器走的是另一条 Shell 解压路径**，不能互相代理。
  - README 明确写着支持 Windows 10。**在拿到 Win10 实测前上 LZMA，风险是"部分用户下载后解压失败"**——这是首次运行体验，代价远大于 27MB。
  - deflate L9 与 L6 **产物完全同体积**（B4 意外发现 5），不必付 L9 的耗时。
- **决策点见 §5.2。**
- **同时**：`copy_tools()` 已经 `ignore_patterns("Logs")`（P3-18 已修），新步骤不需要重复处理。

### B4 · 排除 `PySide6.QtNetwork`（-7.47 MB）

- **位置**：`scripts/build_app.py:30-32` 的 `--exclude-module` 列表（**同 A4，不是 spec**）
- **实测收益（B2 重打包验证）**：

| 文件 | 变化 |
|---|---|
| `PySide6/QtNetwork.pyd` | 消失 -0.96 MB |
| `libssl-3-x64.dll` | 消失 -0.98 MB |

| `Qt6Network.dll` | **保留**（`Qt6Multimedia.dll` 静态导入，B3 已证实） |
| **合计** | **-7.47 MB** |

- **⚠️ 前置条件：GUI 冒烟测试没做。** 报告 B2 明确声明只跑了 `--selftest`（覆盖 4 页构造 + SVG 渲染 + 网络自检），**未覆盖**真实 HTTPS 下载、视频预览播放、设置保存、暗色切换、重启恢复横幅。
- **必须补做的冒烟清单**（实施时随 v1.3.1 测试套件一起）：
  1. 真实 HTTPS 下载一个直链文件（验证 Python 侧 ssl 未受影响）

  4. 设置页改路径 → 保存 → 重启验证持久化

- **另一个流程发现（报告 B2）**：`spec` 与 `build_app.py` 强耦合——**脱离 `build_app.py` 的裸 PyInstaller 产物不可用**（缺 `tools/`，且 `prune_dist()` 没跑，`_internal` 反而大 35.7MB）。建议把这行警告写进 `CONTRIBUTING.md`。

## 4. 批次 C：撤销 / 降级 / 待定

这一节的价值不低于前两节——**它防止把已被实测否掉的方案实施下去**。

### C1 · `avdevice-63.dll` 删除 → **撤销**

B1 实测：删除后 `ffmpeg.exe` / `ffprobe.exe` **启动即失败（rc=127，STATUS_DLL_NOT_FOUND）**，拷回后立即恢复。静态导入，不可删。**放弃这 3.5MB。**

附带确认：运行时模块枚举显示 `tools/` 下 6 个 DLL **全部被加载，无冗余**——这个目录没有可再砍的二进制。

⚠️ 排查记录（报告 B1，值得留存）：Git Bash 把缺失的 `avdevice-63.dll` **误报成 `swscale-10.dll`**。以后查这类问题不要信报错文本，要做恢复对照实验。

### C2 · 进度改读 stderr → **降级为可选，且理由要换**

- 原理由（"18000 帧目录每 0.6s scandir 会与引擎争抢 I/O"）**实测不成立**：18000 帧单次 scandir **5.82ms**，占轮询周期 **0.97%**；并发写入下仅 +2%。50000 帧也只有 2.76%。**我上一轮的断言是错的。**
- P2 已确认 stderr 解析**技术上可行且实时**（150 帧任务的百分比行时间跨度占总时长 99%，首档在启动后 0.2s 出现）。但格式有个关键陷阱：
  > **百分比是"帧内"的，不是"整任务"的**——每帧输出 N 档（N = 该帧的 tile 网格数，`-t auto` 下恒为 15 档，`-t 256` 下 478×858 变 8 档）然后归零重来。不加 `-v` 时没有 `done` 行，**只能靠数 `0.00%` 的出现次数来计帧**。
  > 而 A3 一旦改了 tile，**档数就会变**——解析逻辑不能硬编码 15。
- **结论**：改 stderr 的唯一正当理由是"帧内细粒度进度"（当前 0.6s 粒度在慢模型上体验粗糙：general-x4v3 是 1.8s/帧，x4plus 是 28s/帧，**一帧内进度条完全不动**）。**这才是真需求**，但与性能无关。
- **建议**：若要做，**只对慢模型做**（x4plus 28s/帧、general-x4v3 1.8s/帧），动漫模型 0.4s/帧无必要。且必须保留 stderr 落日志（`proc.py` 的"报障无需复现"设计不能破）。**注意 `proc.py` 的 PIPE 卡死史**（v1.0 事故），读取线程必须 daemon + 异常安全。

### C3 · OOM 自动减半重试 → **重新定义**

S2 结论：**本机（核显 + 统一内存 + 系统管理页面文件）无法复现引擎 OOM。** 尝试到 `-t 2048 -s 4`（GPU 4.4GB）、8 进程并发（Commit 37.9GB，**超过开机时的 34.2GB 上限**）——引擎从未失败，Windows 静默扩页面文件把压力吸收了。

**核显上"显存不足"的真实形态是速度塌方（t2048 比 t1024 慢 12.7 倍）与磁盘抖动，不是一条报错。**

因此：
- **不要实现"捕获 OOM → 减半 tile 重试"**：在本机无法验证，等于上一段未经验证的代码；而且 A3 的方案（重模型留 auto）已经从源头避开了高显存档位。
- **P3-23 拆成两半**：
  - **核显侧（可立即做）**：防呆——tile 配表本身就避免了 t1024 以上档位；另可在预计耗时/显存异常时给出提示（并入 B2 的预检 UI）。
  - **独显侧（待补测）**：真实 `vkAllocateMemory` 失败的报错文本**仍未采集到**，需要一台 2~4GB 显存的独显机器跑 `results/oom_*.json` 里的命令。拿到文本前**不要改 `enhance.py:206-207` 的报错文案**——现在改就是拿猜测替换猜测。
- **一个值得写进文档的用户风险（报告意外发现 4）**：核显用户跑超大任务的真实风险是**页面文件把磁盘写爆 / 系统卡死**，而不是收到一条报错。B2 的预检因此更有必要。

### C4 · 剪切路径改 QSV → **待定，需你决策**

见 §1.3。增量仅 10%（2.48× → 2.73×），代价是多厂商探测 + 回退链 + **nvenc/amf 完全未测**。

若决定做，实现要点（基于我的复核，**不是**报告的原始结论）：
- 必须用 `-hwaccel qsv -hwaccel_output_format qsv` **且去掉 `-pix_fmt yuv420p`**（否则报 `Impossible to convert between the formats supported by the filter`）
- 输出 `yuvj420p`，与当前实现一致，无兼容性回退
- 回退链：全硬件 QSV → 软解硬编 QSV → `libx264 veryfast`（A2 已提供这一档，是天然的安全网）
- **不要**用输入侧 `-c:v h264_qsv` 硬解（实测 2.838s，比软解硬编 2.480s 慢）
- 4K 源下 QSV 的优势会扩大（C1 显示 medium 的成本随像素量增长更快），**若你常切 4K，值得先补一轮 4K 剪切实测再定**

### C5 · 跳过 `eff==1.0` 的空转 lanczos → **撤销**

两轮实测一致：956×1716 差 1.4%；4K 差 -2%（**带 vf 反而快，噪声**）；5K 差 0.2%。不值得改。

### C6 · `-j` 线程调优 → **撤销**

S3：`1:4:2` 相对默认在**全部四个模型**上差异 <±0.5%（方差内）。上一轮在 animevideov3 上测得的 +7.6% **未能复现**。整个维度砍掉，A3 只配 tile。

## 5. 需要你决策的点

### 5.1 剪切路径：只上 `veryfast`，还是再加 QSV？

- **只 veryfast**（推荐）：1 行改动，2.48×，全平台一致，无需显卡探测与回退链，nvenc/amf 未测的风险归零。
- **加 QSV**：再快 10%（2.73×），但需实现厂商探测 + 三级回退，且 AMD/NVIDIA 路径从未验证。
- **折中**：先上 veryfast，等拿到 4K 剪切或多厂商机器的实测数据再决定 QSV。

### 5.2 发行包用 deflate 还是 LZMA？

- **deflate L6**（推荐）：163.6MB，Win10 资源管理器双击必开，无兼容性风险。
- **LZMA**：136.3MB（-27.3MB），但 **Win10 资源管理器行为未实测**。若选它，需要先找一台 Win10 双击验证，或在 README 明确写"Win10 用户请用 7-Zip / Bandizip 解压"。

### 5.3 真人·通用视频模式要不要设上限？

E2E2 的实测数字很硬：10 分钟 1080p → **139.7 GB 中间文件 + 17.3 小时**。这个模式对长视频实际上不可用。选项：

- **仅预检 + 预告**（B2 方案，推荐）：不改能力边界，把数字如实告诉用户，让他自己决定。
- **加软上限**：例如源时长 > 3 分钟时要求二次确认。
- **加硬上限**：直接拒绝超长源。
- 也可以考虑给真人视频提供"先降分辨率再增强"的选项，但这属于新功能，不在本方案范围。

### 5.4 B1（VFR）的优先级

取决于你的实际用法：**主要增强下载的视频（B站/抖音/m3u8）→ 几乎全是 CFR，B1 收益很小，可排在 B2 之后**；**常拿录屏/录制内容增强 → B1 是 4.4 倍收益，应提到批次 A 之后立刻做**。
