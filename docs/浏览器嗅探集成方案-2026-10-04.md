## 1. 决策与理由

### 1.1 采纳什么

`书签脚本.txt` 里那段 bookmarklet 的核心技巧是 **`performance.getEntriesByType('resource')`** —— 它能抓到播放器通过 XHR/fetch 请求的、**在 DOM 里根本不出现**的 m3u8/mpd/媒体地址。这是本项目目前完全缺失的能力。

它解决的问题正好是项目最贵的那一块：**站点适配**。

| 对比维度 | 自建解析（`douyin.py` 路线） | 浏览器嗅探 |
|---|---|---|
| 代码量 | 186 行 / 站点 | 一段通用脚本 |
| 站点改版后 | 失效，需重新逆向 | **不受影响**（只要浏览器能播就能嗅） |
| 登录态 | 需自己处理签名/Cookie | **直接复用用户浏览器的会话** |
| 历史维护成本 | git log 可见多轮修复：403 签名过期、CDN 防盗链 Referer、ttwid 注册 | 无 |
| 打包体积 | 0 | **0** |

### 1.2 不采纳什么，以及为什么

**不移植 `m3u8下载器.html`**：

1. **受 CORS 限制**——它自己的《使用说明》第 67-69 行就写着"少数网站的服务器设置了 CORS 限制，浏览器无法直接获取"。从 `file://` 源去 fetch 第三方 CDN 分片，失败是常态而非例外。
2. **产出物更差**——它合并出裸 `.ts`，说明里还要教用户装 VLC 才能播（第 71-73 行）。
3. **完全重复**——项目已打包 N_m3u8DL-CLI，具备 AES-128 自动解密、自动合并、`--enableMuxFastStart`、多线程分片下载，且**无 CORS 约束**。浏览器内下载是严格劣化的实现。

**不采用 QWebEngineView 内嵌浏览器方案**：QtWebEngine 约 150~200MB，会直接抵消前两轮为 7.47MB / 0.68MB 做的全部轻量化工作（当前 dist 333.5MB）。

**不采用本地代理抓包方案**：HTTPS 需要安装 MITM 根证书，与 README 承诺的"不写注册表、不后台驻留、不上传数据"的隐私立场冲突。

### 1.3 对"下载视频 + 画质增强"这个需求的意义

嗅探本身不提升画质，但它**扩大了可增强的素材来源**。当前 README 兼容性表里标 ❌ 的站点（快手/微博/西瓜/小红书），走嗅探路径后大概率会变成"可下"——下载完就能直接进增强页。这是把两个已有能力强连接起来，不是新增第三种能力。

## 2. 现状勘查（实测事实，非推测）

### 2.1 ⚠️ 阻塞性问题：设置页的 Cookie 与代理只对 1/3 的下载路径生效

| 引擎 | 入口 | Cookie | 代理 | 自定义 header |
|---|---|---|---|---|
| yt-dlp（网站视频） | `download_tab.py:331-332` | ✅ `cookie_file` | ✅ `effective_proxy(...)` | — |
| **N_m3u8DL-CLI（m3u8/MPD）** | `download_tab.py:615-616` | ❌ **未传** | ❌ **未传** | ❌ **未传** |
| **直链下载** | `download_tab.py:611-612` | ❌ **未传** | ❌ **未传** | ⚠️ 仅 `direct_dl.py:186-198` 对抖音硬编码 |

**而 N_m3u8DL-CLI 3.0.2 本身是支持的**（`--help` 实测原文）：

```
--headers          设定请求头，格式 key:value 使用|分割不同的key&value
--proxyAddress     设置HTTP/SOCKS5代理, 如 http://127.0.0.1:8080
--noProxy          不自动使用系统代理
```

**结论**：这不是"要新增能力"，而是"已有能力没接上"。**在修好这一条之前上线嗅探，用户拿到的链接会直接 403，功能看起来就是坏的。**

### 2.2 潜在 bug：`m3u8dl://` 被识别但从未剥离

- `url_detect.py:13` 的正则接受 `m3u8dl://` 前缀
- `url_detect.py:40` 的 `detect_engine()` 把 `m3u8dl://` 判为 m3u8 引擎
- **但 `m3u8_dl.py:45` 把 `self.url` 原样传给 CLI** —— 全仓无任何位置剥离该 scheme

即：用户粘贴 `m3u8dl://https://a.com/x.m3u8` 会被送进 CLI 并失败。

**该 scheme 的来源已查明**：`N_m3u8DL-CLI --help` 里有 `--registerUrlProtocol` / `--unregisterUrlProtocol`（"注册 m3u8dl 链接协议"），即这是 **CLI 自己的协议注册功能**，用户可能从 CLI 生态的浏览器扩展拿到这种链接。所以它不是凭空的死代码，**正确修法是在 `M3u8DownloadTask.__init__` 里剥离前缀**（`url.removeprefix("m3u8dl://")`），而不是从 `url_detect` 里删掉识别。

⚠️ 本项目**不应调用 `--registerUrlProtocol`** —— 它会写注册表，直接违背 README 承诺的"不写注册表"（`审计报告.md` 第三节已把这条列为通过项）。

### 2.2.1 附带查明：MPD 支持是真实的（README 没说错）

`--help` 的 42 行完整选项里**没有任何 mpd/dash 字样**，一度让人怀疑 README 宣称的"m3u8 / HLS / **MPD**"是错的。但检查 exe 的 .NET 元数据类型名发现存在 **`MPDParser`** 类 —— **MPD 解析能力是有的，只是靠内容自动识别、不作为命令行选项暴露**。

因此：
- `url_detect.py:40` 把 `.mpd` 路由到 m3u8 引擎是**正确的**，不是 bug
- §2.3 的改进 ①（补 `.mpd` 识别）**成立且有价值**
- 但端到端是否真能下载一个 `.mpd`，**仍未实测**（见 §6 实测清单 T4）

> 方法论备注：对 .NET 程序集，ASCII 字节搜索不可靠（字符串常量是 UTF-16，实测 `.m3u8` 字面量命中 0 次而 `m3u8` 命中 85 次），但 **#Strings 元数据堆里的类型名是 UTF-8，可靠**。判断能力有无应查类型名，不要只查 `--help`。

### 2.3 原书签脚本的三处不足

| # | 问题 | 影响 |
|---|---|---|
| 1 | **不识别 `.mpd`（DASH 主清单）** | 脚本只匹配 m3u8 / m4s / 常见音视频扩展名。而 CLI 确有 `MPDParser`（见 §2.2.1）、`detect_engine` 也认 `.mpd`，所以嗅到 `.mpd` 是能直接下的。**⚠️ 但不要期待这能解锁 B站**——见 §2.4 的真机实测：B站页面里 `.mpd` 命中 **0** 次，它的 DASH 清单是通过 playurl 接口以 JSON 内联下发的，不存在可嗅探的 `.mpd` 文件请求。此改进对**其它以文件形式提供 .mpd 的站点**有效 |
| 2 | **不输出来源页 URL** | 嗅探到的 CDN 链接几乎都需要原页面作 Referer。`direct_dl.py:186-189` 的注释已经记录过教训："拿播放链接自身的域名当 Referer 会被防盗链 403，固定用站点页 Referer 实测 200"。**不带上来源页，用户就没法填 Referer** |
| 3 | **`performance` 资源缓冲区上限** | 默认 250 条。**实测行为见 §2.4——与我最初的判断相反** |

### 2.4 真机实测（Chrome + B站真实视频页）

用真实浏览器打开 `bilibili.com/video/BV1GJ411x7h7`，等媒体请求发生后扫描 `performance` 资源表：

| 指标 | 实测值 |
|---|---|
| 资源条目总数 | **233**（已逼近 250 上限） |
| `.m3u8` 命中 | **0** |
| `.mpd` 命中 | **0** |
| `.m4s` 命中 | **40** |
| `.mp4` / 音频文件命中 | **0** |
| DOM `<video>.src` | `blob:https://www.bilibili.com/0c90a6aa-…`（MSE） |
| m4s URL 的 `deadline` 参数 | `1791111383` → **签发后约 2 小时失效**（实测剩余 118.7 分钟） |

**三个结论**：

1. **B站嗅探不到任何可用清单** —— 它是 MSE + `blob:` + 内联 JSON 下发的 DASH，页面里既无 `.m3u8` 也无 `.mpd` 文件请求，只有 40 个签名 `.m4s` 分片。**但这对本方案没有损失**：B站本来就走 yt-dlp 且工作正常（V2 轮已实测 3 个 B站样本下载成功）。嗅探的目标是 yt-dlp 覆盖不到的站点，不是 B站。
2. **签名 URL 有效期约 2 小时**（B站实测）—— 比预想宽松。"嗅探→粘贴→下载"的连贯操作有充足时间窗，§5 的风险 2 可以降级，但报错文案仍应提示"链接可能已过期，请重新提取"。
3. **缓冲区溢出的真实行为与直觉相反** —— 见下。

#### 缓冲区溢出行为（实测，纠正 §2.3 的第 3 条）

把缓冲区上限压到 10，先取 5 条早期资源、再打 40 条后续资源：

```
bufferSizeSetTo: 10
afterOverflow: { totalEntries: 10, earlyStillPresent: 5, fillRecorded: 5 }
conclusion: EARLY_KEPT_new_dropped
```

**溢出时保留的是早期条目、丢弃的是新条目**——不是"长播放会丢早期条目"。

对本方案是**有利**的：媒体清单在播放开始时就被请求，属于早期条目，即使页面后续加载几百个分片也不会被挤掉。B站 那 233 条里 40 个 m4s 全在，也印证了这点。

**真正的风险场景只剩一个**：页面在**播放开始之前**就已经填满 250 条（B站 的 233 条已经很接近）。此时清单请求会被丢弃。

所以脚本里那句提示的**理由要改**（提示语本身仍成立）：不是"长播放会丢"，而是"页面在播放前已把缓冲区填满时，清单可能没被记录 → 刷新页面后立即播放并点击书签"。

#### S1.3 新增 `app/cookiejar.py`：cookies.txt → Cookie 头

设置页存的是 **Netscape 格式 cookies.txt**（`settings_tab.py:39-43`），yt-dlp 能直接吃，但 N_m3u8DL-CLI 和 urllib 需要的是 `Cookie: k=v; k2=v2` 请求头。需要一个转换：

```python
def cookie_header(cookie_file: str, url: str) -> str:
    """从 Netscape cookies.txt 中挑出适用于 url 的条目，拼成 Cookie 头值。
    文件不存在/格式错/无匹配条目时返回 ''（绝不因此让下载失败）。"""
```

要点：
- Netscape 格式是 **Tab 分隔 7 列**：`domain  flag  path  secure  expiry  name  value`，`#` 开头为注释（但 `#HttpOnly_` 前缀行是有效条目，必须处理）
- **按域名匹配**：`.bilibili.com` 应匹配 `www.bilibili.com`；不能把 A 站的 Cookie 发给 B 站（**这是隐私与安全的硬要求**）
- 过期条目（`expiry < now`）应跳过
- **任何解析失败都返回 `''` 并继续下载**，不能因为 Cookie 文件坏了就让本来能匿名下载的链接失败

#### S1.4 `app/download_tab.py` 传参

第 611-616 行两处构造补上 `cookie_file=self.settings.cookie_file`、`proxy=effective_proxy(...)`、`referer=<见 S3>`。

##### 为什么不用 `window.open` + clipboard（T1 的处置）

上一版脚本的结果界面靠 `window.open` 弹窗 + `navigator.clipboard.writeText` 按钮。这两件事**在 mock 环境里永远成功**（mock 的 `window.open` 返回对象、`writeText` 永远 resolve），而我在真机探测时浏览器会话一度失去响应——最可疑的正是 clipboard 的权限询问。与其去测两个浏览器各自的弹窗/剪贴板策略，不如**从设计上不依赖它们**：

| 风险 | 旧写法 | 新写法 |
|---|---|---|
| 弹窗被拦 → 用户以为书签没反应 | `window.open('','_blank',...)` | **注入当前页**：`div` + `attachShadow({mode:'open'})` + `position:fixed` 覆盖层 + 「关闭」按钮 |
| clipboard 权限被拒 → 复制静默失败 | 按钮 `onclick` 里只调 clipboard | **单击链接即原生全选**（`user-select:all`），`Ctrl+C` 一定可用；clipboard 只是加速路径，失败时按钮文案降级为「已选中」 |
| 页面 CSS 污染结果界面 | 新窗口，天然隔离 | **shadow root** 隔离宿主样式 |
| 页面 CSP 拦 `<style>` / `style="..."` 字符串 | 未考虑 | **全部样式走 CSSOM 属性赋值**（`e.style.position='fixed'`），不发 `<style>`、不发 style 字符串、不用 `setAttribute('style',...)` |
| URL 含 `"` `<` 破坏 HTML 结构 | `document.write` 拼字符串 | **零 HTML 拼接**：一律 `textContent` / CSSOM，`innerHTML` 与 `document.write` 在源码里根本不出现（有断言把关） |
| 暗色模式 | `@media(prefers-color-scheme:dark)` 写在 `<style>` 里（会被 CSP 拦） | `matchMedia("(prefers-color-scheme:dark)").matches` 选色值，再走 CSSOM 赋值 |

**三级降级链**（每级都实测过）：
1. `attachShadow` 成功 → shadow DOM 覆盖层（正常路径）
2. `attachShadow` 抛错 → **同一批元素直接挂进光 DOM**（样式全靠内联 CSSOM，不依赖样式表，因此不降级）
3. `documentElement.appendChild` 也抛错 → `window.open("about:blank")` + 纯 `textContent` 列表；连弹窗也被拦时 `alert` 引导用控制台，**绝不静默失败**

##### 脚本必须保持单行才能当书签 URL —— 压缩规则已固定

`snippet.src.js` 是多行可读源，但书签 URL 不能带换行。**压缩规则就一句**（已实测与源文件行为完全一致，70/70 通过）：

```python
bookmarklet = "javascript:" + " ".join(l.strip() for l in src.splitlines() if l.strip())
```

- 压缩后 **6096 字节**（UTF-8）。Chrome/Edge 早已解除书签长度限制，但**仍需在 T6 里确认目标浏览器接受这么长的书签 URL**。
- ⚠️ **禁止改成"逐行首尾直接相连"**：源文件里有 `}` 与 `else if` 跨行的语句，无分隔符相连会改变语义。必须用空格。

#### S3.2 用 URL fragment 携带 Referer —— **不新增任何控件**

> **这一节推翻了我最初的方案。** 原本打算加一个「来源页 Referer」输入框，但实测发现 fragment 方案更好，而且原方案有个正确性缺陷。

**原方案（输入框）的两个问题**：

1. 违背「简洁现代化 · 能删的控件先删」的取向，多一个常驻控件。
2. **更严重：作用域是错的。** 单个输入框只能作用于"本批全部任务"，而用户批量粘贴**来自不同页面**的嗅探链接时，共享一个 Referer 必然对部分是错的。

**改用 fragment 方案**：书签脚本复制出的链接形如

```
https://cdn.a.com/video.mp4#sgref=https%3A%2F%2Fwww.page.com%2Fwatch%2F1
```

fragment（`#` 之后）**不会被浏览器和 HTTP 客户端发送给服务器**，所以它是天然的带外元数据通道；而每条链接自带自己的 Referer，批量场景天然正确。

**实测验证：这个形态能完整穿透现有识别链**

| 输入 | `extract_urls` | `detect_engine` |
|---|---|---|
| `https://a.com/x.m3u8#sgref=https%3A%2F%2Fwww.page.com%2Fwatch%2F1` | 原样保留 ✅ | `m3u8` ✅ |
| `https://a.com/x.m3u8#sgref=https://www.page.com/watch/1`（未编码） | 原样保留 ✅ | `m3u8` ✅ |
| `https://cdn.a.com/v.mp4#sgref=https://www.page.com/p` | 原样保留 ✅ | `direct` ✅ |

能穿透的原因：`URL_RE` 的排除字符集不含 `#` 和 `=`，且 `quote(..., safe=":/?#[]@!$&'()*+,;=%~")` 把 `#`、`=`、`%` 都列为安全字符。

**⚠️ 实测发现一个必须处理的坑：`detect_engine` 会被 Referer 里的字样误导**

| 输入（媒体是 .mp4，但来源页路径含 `.m3u8`/`.mpd`） | 实测 `detect_engine` | 应为 |
|---|---|---|
| `.../video.mp4#sgref=...%2Fplayer.m3u8.html` | **`m3u8`** ❌ | `direct` |
| `.../video.mp4#sgref=...%3Ff%3Dindex.mpd` | **`m3u8`** ❌ | `direct` |

根因：`url_detect.py:40` 是 `".m3u8" in low` 的**全串子串匹配**，会把 fragment 里的字样也算进去。

**修法**：`detect_engine()` 在做任何匹配**之前**先剥离 `#sgref=` 片段。这一条必须与 fragment 方案同批实施，否则引入回归。

#### S3.2.1 实施细节

**① `app/url_detect.py` 新增拆分函数**

```python
SGREF = "#sgref="

def split_referer(url: str) -> tuple[str, str]:
    """拆出书签脚本用 #sgref= 携带的来源页。返回 (纯媒体URL, referer)。

    没有 sgref 片段时 referer 为 ''，纯媒体URL 即原串——
    因此对既有全部链接形态是完全透明的。
    """
    i = (url or "").find(SGREF)
    if i < 0:
        return url, ""
    return url[:i], urllib.parse.unquote(url[i + len(SGREF):])
```

**② `detect_engine()` 先剥离再匹配**（`url_detect.py:34-46`）

```python
def detect_engine(url: str) -> str:
    u, _ref = split_referer((url or "").strip())   # ← 新增：先剥离
    low = u.lower()
    ...                                            # 其余逻辑不变
```

`url_media_kind()`（第 49-59 行）同理，它也是 path 后缀匹配。

**③ 引擎侧消费 Referer**

- `download_tab.py` 派发前调 `split_referer()`，把 `(纯URL, referer)` 分别传给 `M3u8DownloadTask` / `DirectDownloadTask`（S1 已加好 `referer` 参数）
- **`referer` 为空时必须完全保持现有行为**：`direct_dl.py:186-198` 那套抖音 Referer 推断逻辑不能被覆盖（那是实测得出的：CDN 域名做 Referer 会 403，站点页做 Referer 才 200）。规则：**用户/脚本显式给了 Referer 就用它，否则走原有推断**
- 走 yt-dlp 的链接：把 referer 传成 `opts["http_headers"]["Referer"]`

**④ 书签脚本侧**（改 S2.2 的 `sec()` 复制按钮）

### 6.2 待实测 · P0（不测则功能可能静默失效）

> 原本这一节有 T1/T2/T3 三项。**T1 已闭环**（改为设计规避 + 真机验证），列在这里只为保留判断轨迹；**真正的剩余门槛是 T2、T3 两项**。

#### T1 · 弹窗拦截 与 clipboard 权限 → **已闭环（改为按设计规避 + 真机已验）**

**原风险**：结果界面依赖 `window.open('','_blank',...)`，复制依赖 `navigator.clipboard.writeText`。真机探测时浏览器会话一度失去响应，未能取得结论。

**处置**：不采用"先测再改"，直接换成**不依赖这两个 API** 的覆盖层设计（§S2.2），并已在真机 Chrome + B站页面完成渲染与选中行为验证（§S2.2.1 B）。

- `window.open` 从主路径移除，只作为第三级兜底保留（且该兜底本身也在 mock 里跑过）
- clipboard 从"唯一复制手段"降为"加速路径"，主手段是 `user-select:all` + `Ctrl+C`，实测载荷逐字精确
- 因此 **T1 不再是发布门槛**。仍需真人验收的只剩两件事，均已并入 T6：
  1. 桌面 Chrome / Edge 书签栏点击 `javascript:` 是否真执行、多长的书签 URL 会被拒
  2. 覆盖层在**带严格 CSP 与自定义样式重置**的站点上是否仍可见（B站实测无 CSP，样本单一）

#### T2 · `--headers` 的分隔符与转义行为

**为什么**：CLI help 只写了"格式 `key:value` 使用 `|` 分割不同的 key&value"。但真实 Cookie 值里**必然含 `;`**（多个 kv 的分隔）、**可能含 `:`**（如 `expires` 或 base64 里的字符），个别站点 Cookie 值甚至含 `|`。**解析规则未知，猜错就是静默 403。**

**怎么测**：用一个真实需要 Cookie 的 m3u8/mp4 链接，分别试：
1. 只带 `Referer`（不含特殊字符）→ 是否生效
2. 带 `Cookie:a=1; b=2`（含 `;` 和空格）→ 是否生效
3. 带含 `:` 的 Cookie 值 → 是否生效
4. 三个 header 用 `|` 拼接 → 是否都生效
5. 构造一个值里含 `|` 的 header → 观察是失败还是被截断

可先用 `--enableParseOnly` 快速验证（只解析不下载，省时间），或起一个本地 HTTP 服务打印收到的请求头——**后者最可靠**，能直接看到 CLI 实际发出了什么。

**判定标准**：给出"哪些字符安全、哪些需要转义/不可用"的明确结论。若 `|` 无法转义，则含 `|` 的 Cookie 必须放弃并给出提示。

#### T3 · 嗅探 → 下载 端到端闭环（真实 m3u8 站点）

**为什么**：这是整个方案的核心假设——"浏览器里能播的 m3u8，交给 N_m3u8DL-CLI 就能下"。**至今没有任何一次真实验证。** B站已被实测排除（无 m3u8，§2.4）。

**怎么测**：找一个真实提供 `.m3u8` 的页面（HLS 测试流、或用户常用的站点），完整走一遍：装书签 → 播放 → 点书签 → 复制 → 粘进应用 → 下载成功 → 成品可播放。

**判定标准**：
1. 书签能否嗅到 `.m3u8`（含多级 variant playlist 的情况）
2. 复制出的链接（带 `#sgref=`）粘进应用后，`detect_engine` 是否为 `m3u8`
3. **`#sgref=` 是否在传给 CLI 前被正确剥离**（否则 CLI 会拿到带 fragment 的 URL 而失败）
4. 下载成功、成品时长与源一致、可正常播放

## 9. 四个悬置问题的处置记录

> 上一版本文档在这里留了四项待确认。按"提问前先多检查几遍"的要求逐一查证：**9.1~9.3 的答案在代码里或已被实测否掉，不需要你决策**；**9.4 是唯一真正属于取舍的一项，你已拍板，且我已把它实现并验证完毕**。记录如下，便于你复核我的判断是否成立。

### 9.1 S1 的范围 → 决定：做全量（Cookie + 代理 + Referer）

原问题：是否同意"即使不做嗅探也先修 S1"，还是缩到只加 Referer。

**查证结果**：不需要权衡。`cookie_header()`（S1.3）是**让设置页已有的 Cookie 选项对 m3u8 与直链生效**的唯一缺口——这个功能用户已经能配置、UI 已经存在、文档已经写了，只是**两条路径根本没接**。缩小范围等于明知有缺陷而只修一半，且省下的工作量很小（Cookie 解析是 S1 里最独立的一块，加不加 Referer 都得写）。

**决定**：S1 全量实施，且**排在嗅探功能之前**。

### 9.2 Referer 输入框 → 决定：不加，改用 URL fragment

原问题：是否接受多一个常驻输入框。

**查证结果**： fragment 方案实测可穿透现有识别链（§S3.2 表），**零新增控件**。而且原输入框方案有个我此前没发现的正确性缺陷——它的作用域是"本批全部任务"，而批量粘贴来自**不同页面**的嗅探链接时，共享一个 Referer 必然对部分是错的。fragment 天然做到每链接独立。

**决定**：采用 fragment，不加任何控件。连带必修 `detect_engine` 的子串误判（§S3.2 已实测确认存在）。

### 9.3 直播流的停止引导 → 决定：不需要新增任何东西

原问题：是"如实告知限制"还是"加个停止按钮"。
