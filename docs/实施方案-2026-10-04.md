### U1 · 补齐无协议头 / 裸短链 / 纯 BV 号

**文件**：`app/url_detect.py`

**设计原则**：**不改现有 `URL_RE`**（它已经处理好了中文标点截断、口令剥离、多链接等所有边界），而是**加两条独立的补充规则**，最后统一归一化 + 去重。这样既有行为零回归风险。

**① 新增两个常量**（放在 `URL_RE` 之后）：

```python
# 无协议头时也允许识别的主机白名单。只收录 README 兼容性表里的站点 +
# 常见短链，不做成"任意裸域名都当链接"——否则普通英文句子里的
# "example.com" 会被误抓。新增站点时同步更新 README 的兼容性表。
BARE_HOSTS = (
    "b23.tv", "bili2233.cn", "bilibili.com",
    "douyin.com", "iesdouyin.com",
    "weibo.com", "weibo.cn", "t.cn",
    "xiaohongshu.com", "xhslink.com",
    "kuaishou.com", "chenzhongtech.com",
    "ixigua.com", "haokan.baidu.com",
    "youtube.com", "youtu.be",
    "x.com", "twitter.com", "t.co",
)

# 裸主机匹配：白名单主机（可带 www./m. 前缀）+ 后续非空白非标点串
BARE_RE = re.compile(
    r"(?<![\w./-])(?:www\.|m\.)?(?:"
    + "|".join(re.escape(h) for h in BARE_HOSTS)
    + r")/[^\s，。；、）】》」』\"“”‘’<>『「\u4e00-\u9fff]*",
    re.IGNORECASE)

# 纯 BV 号（B 站视频编号，BV + 10 位字母数字）
BV_RE = re.compile(r"(?<![0-9A-Za-z])BV[0-9A-Za-z]{10}(?![0-9A-Za-z])")
```

**② `extract_urls()` 改为三趟收集 + 统一归一化**：

```python
def extract_urls(text: str):
    """从任意粘贴文本提取 URL 列表（保持顺序、自动去重、容忍中文标点）。

    三趟：带协议头的 URL → 无协议头的白名单主机 → 纯 BV 号。
    归一化后统一去重，因此 "BV1xx" 与含同一 BV 号的完整链接不会重复。
    """
    text = text or ""
    urls, seen = [], set()

    def add(raw: str):
        u = raw.rstrip(".,;:!?)'\"，。；：！？）】》”’")
        if len(u) <= len("http://a.bb"):
            return
        # 非 ASCII 字符做百分号编码（对齐浏览器行为），
        # 避免带中文的直链在后续网络请求里以 ascii 编码崩溃
        u = urllib.parse.quote(u, safe=":/?#[]@!$&'()*+,;=%~")
        key = u.lower()
        if key not in seen:
            seen.add(key)
            urls.append(u)

    for m in URL_RE.findall(text):
        add(m)
    for m in BARE_RE.findall(text):
        add("https://" + m)
    for m in BV_RE.findall(text):
        add(f"https://www.bilibili.com/video/{m}")
    return urls
```

**要点**：
- `add()` 里的 `rstrip` / 长度过滤 / 百分号编码**逐字沿用原实现**（原第 21-26 行），只是收进闭包，避免三份重复。
- **顺序不能变**：先带协议头、再裸主机、最后 BV 号。因为 `seen` 去重是"先到先得"，若 BV 号先跑，`https://www.bilibili.com/video/BV1xx` 会被展开成同一个 URL 而让原始链接反而进不去——虽然结果 URL 相同，但保持"用户原文优先"更可预期。
- `BARE_RE` 的 `(?<![\w./-])` 负向断言用于避免匹配到已有协议头的 URL 尾部（`https://www.bilibili.com/...` 里的 `www.bilibili.com/...` 片段）。**这一条必须有，否则每个带协议头的 B 站链接都会被重复匹配一次**（虽然去重会兜住，但白跑一趟且顺序会乱）。
- `detect_engine()` / `url_media_kind()` **完全不用改**——补上 `https://` 之后走的是既有路径。

#### B2.1 估算系数（从两轮实测数据回归得出）

**耗时**：逐点核算后发现单帧耗时与**源像素量**成正比，拟合优度 ±3%：

| 模型 | 系数（秒 / 源百万像素 / 帧） | 拟合来源 |
|---|---|---|
| `realesr-animevideov3` | **0.93** | S1 四个分辨率：0.929 / 0.954 / 0.933 / 0.916 |
| `realesr-general-x4v3` | **2.05** | S3（1.96）+ E2E2（2.09） |
| `realesrgan-x4plus-anime` | **9.1** | S3：8.41 s/帧 ÷ 0.92 Mpx |
| `realesrgan-x4plus` | **28.4** | S3：26.1 s/帧 ÷ 0.92 Mpx |

上表均在 `-s 2`（animevideov3）/ `-s 4`（其余）下测得。其它倍数按 `× (实际 m_scale / 表中 m_scale)` 线性放大，**这是保守方向**（宁可高估耗时）。整体估算精度约 ±20%——**够用于阈值判断，不足以显示精确剩余时间**，UI 只给粗粒度档位。

**磁盘**：

```
输出帧字节/像素：实测 0.295（真人 8K 中间帧）~ 0.461（动漫 956×1716）→ 取 0.46（保守）
输入帧字节/像素：实测 0.0885（1080×1920, qscale:v 1）→ 取 0.10
输出像素 = 源宽 × 源高 × m_scale²
帧数     = fps × 时长(s)
中间文件总量 ≈ 帧数 × (0.46 × 输出像素 + 0.10 × 源像素)
```

对 E2E2 的 195 帧回代：估算 2.97 GB vs 实测 1.9 GB（**保守 1.56×**）；10 分钟外推 220 GB vs 报告 139.7 GB。**故意保守**——预检宁可误拦不可漏拦。

#### B2.2 代码结构

**① `app/utils.py` 新增 `probe_media()`**（一次 ffprobe 拿全部信息）

现状是 `cut_engine.probe_duration()` 与 `enhance.probe_fps()` 各自起一次 ffprobe 进程。预检需要 dur + w + h + fps 四项，**合并成一次调用**，顺带减少一个子进程：

```python
def probe_media(src: str) -> tuple[float, int, int, float]:
```

```python
def make_zip():
    """打包发行 zip（LZMA）。此前仓库无任何生成 zip 的代码，发行包靠手工压缩、不可复现。"""
    import zipfile
    src = os.path.join(DIST, APP_NAME)
    out = os.path.join(DIST, f"{APP_NAME}-v{APP_VERSION}.zip")
    if os.path.exists(out):
        os.remove(out)
    with zipfile.ZipFile(out, "w", zipfile.ZIP_LZMA) as z:
        for root, _d, files in os.walk(src):
            for f in sorted(files):
                p = os.path.join(root, f)
                z.write(p, os.path.relpath(p, DIST))
    print(f">> 发行包 {os.path.getsize(out) / 1048576:.0f} MB → {out}")
```

**所以在拿到真实样本链接做诊断之前，无法估算工作量。** 这也是为什么 U2 不能直接进实施方案。

### 8.3 建议的诊断步骤（需要真实链接）

第二轮报告的 agent 已经卡在"拿不到真实分享链接"上（抖音热榜 API 失效、搜索引擎不收录、代理未监听）。**这一步需要你提供样本**：

对每个目标站点，提供 1~2 个**真实可访问**的链接，然后跑这个矩阵：

| # | 条件 | 目的 |
|---|---|---|
| 1 | 裸跑（无 Cookie 无代理） | 复现失败，抓 yt-dlp 原始报错 |
| 2 | + Cookie | 判断是否登录态问题 |
| 3 | + 代理 | 判断是否网络可达性问题 |
| 4 | + 站点专属 UA/Referer | 判断是否反爬 |
| 5 | 用 yt-dlp 命令行直接跑同一链接 | **隔离变量**：区分"yt-dlp 本身不行"还是"本项目集成有问题" |

第 5 项是关键——`venv/Scripts/yt-dlp.exe <url>` 直接跑，若命令行成功而应用失败，问题就在 `ytdlp_dl.py` 的 opts 组装，成本极低。

诊断产出后，每个站点会落到三类之一：
- **A 类（改文案即可）**：需要 Cookie/代理，功能本来就通 → 只需在 `errors.py` 的报错翻译里给出准确指引，并修正 README 表格
- **B 类（小改集成）**：本项目传参有问题 → 改 `ytdlp_dl.py`
- **C 类（需自建解析）**：yt-dlp 无提取器或已失效 → 像 `douyin.py`（186 行）那样自建。**这是唯一的大成本项，目前已知只有快手落在这里**

### 8.4 关于快手（唯一确认的 C 类）

yt-dlp 确实无提取器。选项：

1. **自建解析**：参照 `app/douyin.py` 的做法（短链展开 → 取 ttwid → 解析播放页 → 拿无水印直链）。工作量参照 douyin.py 的 186 行，但**快手的反爬强度、接口稳定性、是否需要登录态均未知**，实际成本可能远高于抖音。且这类自建解析是**持续维护负担**——站点一改版就失效（抖音已经历过 403 签名过期、Referer 防盗链等多轮修复，见 git log）。
2. **不做，修正 README**：把"暂无解"改成准确表述（"yt-dlp 未收录，本站暂不支持"），避免用户误以为是配置问题。
3. **等上游**：定期升 yt-dlp（当前 2026.08.19），收录后自动生效——**这条几乎零成本，且对全部 C 类站点都适用**，建议无论如何都做。

**我的建议：先做 3（零成本），再按你的实际需求决定 1 或 2。** 自建解析的长期维护成本在抖音那几轮修复里已经看得很清楚，为单个站点投入需要谨慎。

### 8.5 可以立刻做、无需样本的两件事

1. **修正 README 兼容性表**（§8.1 的三处错误）。微博和好看视频被标成"暂无解"会让用户直接放弃尝试，而它们其实可能只差一个 Cookie。**这是纯文档改动，零风险。**
2. **在 `errors.py` 里补站点级引导**：当 yt-dlp 报 `HTTP 401/403` 或 `login required` 类错误时，按域名给出"请到 设置 → Cookie 粘贴 xx 站点的 Cookie"这样的具体指引，而不是通用报错。需要先看一下 `errors.py` 现有的翻译覆盖度。
