# 视频下载失败诊断与修复文档

诊断日期：2026-10-02
诊断对象：`dist/拾光工具箱/拾光工具箱.exe`（桌面快捷方式指向此产物，构建于 10-02 00:59）
现象：只有 B 站能下载，其他网站全部失败。

---

## 一、结论速览

**不是打包问题，也不是解析算法被抖音封了。** 打包产物自检通过（`拾光工具箱.exe --selftest` 退出码 0），
yt-dlp 版本 `2026.08.19`（很新），1752 个 extractor 全部完整打进 `_internal/yt_dlp/extractor/`（941 个 .py）。

真正的根因是**两条能力缺失 + 七个具体缺陷**：

| # | 问题 | 类型 | 影响面 | 优先级 |
|---|------|------|--------|--------|
| 1 | 全项目零 cookie 支持 | 能力缺失 | 所有需登录态的国内站点 | **P0** |
| 2 | 全项目零代理支持，且探测无整体超时 | 能力缺失 | 所有境外站点 + 界面卡死 2 分钟 | **P0** |
| 3 | `errors.py` 缺 cookie/代理关键词映射 | 缺陷 | 报错全是「解析失败（DownloadError）」 | **P0** |
| 4 | 抖音口令 URL 被尾部中文污染 | 缺陷 | 抖音（无空格粘贴时必崩） | P1 |
| 5 | 抖音 `filter_list` 被丢弃 | 缺陷 | 抖音权限类失败无法自解释 | P1 |
| 6 | `DouyinDownloadTask` 的直链缓存从未生效 | 缺陷 | 抖音（含一条会真失败的路径） | P1 |
| 7 | 网络/解析失败不落日志 | 缺陷 | 报障只能靠复现 | P1 |
| 8 | README 与界面文案过度承诺 | 文档 | 用户预期错位 | P2 |
| 9 | 部分站点 yt-dlp 本身无 extractor | 外部限制 | 快手、好看视频等 | 不可修 |

## 二、实测证据

### 2.1 九站点横向测试（venv，`socket_timeout=15`）

| 站点 | 结果 | 原始报错 | 耗时 |
|------|------|----------|------|
| bilibili | ✅ OK | `ie=BiliBili formats=15` | 2.1s |
| douyin | ❌ | `[Douyin] Fresh cookies (not necessarily logged in) are needed` | 0.3s |
| youtube | ❌ | `Unable to download API page: timed out (TransportError)` | **120.3s** |
| kuaishou | ❌ | `Unsupported URL` | 1.8s |
| ixigua | ❌ | `[Ixigua] Cookies (not necessarily logged in) are needed` | 0.4s |
| weibo | ❌ | `TypeError: 'NoneType' object is not subscriptable` | 1.6s |
| xiaohongshu | ❌ | `No video formats found!` | 1.0s |
| twitter/X | ❌ | `Unable to download JSON metadata: timed out` | 15.1s |
| haokan(百度) | ❌ | `Unsupported URL` | 0.4s |

**9 个站点只有 1 个通过**，与用户描述完全一致。失败聚类后只有三种形态：
需要 cookie、需要代理、yt-dlp 无 extractor。

### 2.2 抖音自建解析链路是通的

绕开 yt-dlp 单独跑 `app/douyin.py`，全链路成功：

```

端到端下载    -> 10,932,171 字节 mp4，文件头 b'\x00\x00\x00 ftypisom'（合法 mp4）
```

四种 UA / Referer 组合（桌面 UA+Referer、`Mozilla/5.0` 无 Referer、移动 UA、移动 UA+抖音 Referer）
**全部返回 200 / video/mp4**，说明上一次提交的 403 修复有效，直链侧没有风控问题。

### 2.3 浏览器 cookie 方案在本机也不可用

试过 yt-dlp 的 `cookiesfrombrowser`，两个浏览器都失败：

| 浏览器 | 报错 | 原因 |
|--------|------|------|
| Edge | `Could not copy Chrome cookie database`（yt-dlp#7271） | 浏览器运行中，SQLite 数据库被独占锁 |
| Chrome | `Failed to decrypt with DPAPI`（yt-dlp#10927） | Chrome 127+ 的 App-Bound Encryption，DPAPI 解不开 |

**结论：cookie 方案必须走用户手动导出的 `cookies.txt`（Netscape 格式），不能依赖自动读浏览器。**
这是 P0 方案的关键约束——不要实现成「选择浏览器」下拉框，那个在 2026 年的 Windows 上基本是坏的。

## 三、根因详解

### 根因 1：没有 cookie 支持（影响面最大）

`app/ytdlp_dl.py:207-223` 的 `opts` 字典和 `app/ytdlp_dl.py:17-46` 的 `build_ytdlp_opts()`
里**完全没有** `cookiefile` / `cookiesfrombrowser` 两个键。全项目 grep `cookie` 只命中
`app/douyin.py` 里手搓的 ttwid，没有任何用户可配置的 cookie 入口。

后果：抖音（走 yt-dlp 兜底时）、西瓜视频直接拒绝；小红书拿不到任何 format；
B 站高清（1080P+ / 大会员画质）同样需要 cookie 才能解锁——现在能下只是因为它降级到了免登录画质。

**这是「只有 B 站能用」的第一主因。**

### 根因 2：没有代理支持，且探测没有整体超时

同样在 `opts` 里没有 `proxy` 键。GUI 程序从快捷方式启动，进程环境里没有 `HTTP_PROXY`/`HTTPS_PROXY`，
yt-dlp 也**不读** Windows 注册表里的系统代理（`HKCU\...\Internet Settings\ProxyServer`）。
用户机器上装了 FlClash / Proton VPN，但只要不是 TUN 模式，App 的请求就是裸连，境外站点必然超时。

更糟的是超时体验：`app/ytdlp_dl.py:124` 设了 `socket_timeout: 15`，但实测 YouTube 整体耗时 **120.3 秒**
——因为 yt-dlp 的 extractor 内部还会重试（`_download_webpage` 默认 retries=10），
`socket_timeout` 只管单次 socket 操作，管不住总时长。

而 `_start_probe()`（`app/download_tab.py:312`）在用户停止输入 900ms 后就自动触发，
所以粘一个 YouTube 链接进去，界面会在「正在解析…」上**转两分钟**；
如果用户接着点下载，`YtdlpTask` 再解析一遍，**再转两分钟**。没有任何整体 deadline。

### 根因 3：报错翻译覆盖不足

`app/errors.py:17-42` 的 `KEYWORD_MAP` 有 25 条映射，但**没有一条覆盖 cookie**。
把 2.1 的真实报错灌进 `friendly_error()`，用户实际看到的是：

| 原始报错 | 用户看到 |
|----------|----------|
| `Fresh cookies (not necessarily logged in) are needed` | `解析失败（DownloadError）` |
| `[Ixigua] Cookies (not necessarily logged in) are needed` | `解析失败（DownloadError）` |
| `[XiaoHongShu] No video formats found!` | `解析失败（DownloadError）` |
| `Failed to decrypt with DPAPI` | `解析失败（DownloadError）` |
| `Could not copy Chrome cookie database` | `解析失败（DownloadError）` |
| `TypeError: 'NoneType' object is not subscriptable` | `解析失败（TypeError）` |
| `Unable to download API page: timed out` | `下载数据失败` |
| `Unsupported URL` | `不支持的网站链接` ✅ |
| `Sign in to confirm you're not a bot` | `该内容需要登录，暂不支持` ✅ |

**最高频的四种失败全部塌缩成同一句无信息量的「解析失败（DownloadError）」。**
用户无法区分「这个站点要登录」「我的网不通」「程序有 bug」，
于是合理地推断为「这软件只支持 B 站」。这一条直接决定了用户对产品的判断，修它性价比最高。

### 根因 4：抖音口令 URL 被尾部中文污染

`app/url_detect.py:9`：

```python
URL_RE = re.compile(r"(?:m3u8dl://|https?://)[^\s，。；、）】》」』\"“”‘’<>『「]+", re.IGNORECASE)
```

排除集里有中文**标点**，但没有中文**字符**。抖音口令粘贴进来若链接后紧跟文字（无空格），实测提取结果：

```
输入: 7.99复制打开抖音，看看【张三的作品】https://v.douyin.com/iRNBho6u/复制此链接，打开Dou音搜索
提取: https://v.douyin.com/iRNBho6u/复制此链接
```

后续 `expand_short()` 直接崩在 http.client 的 ASCII 编码上：

```
DouyinError: 短链打开失败：'ascii' codec can't encode characters in position 14-18: ordinal not in range(128)
```

用户看到的是一句英文技术错误。这个洞**不止影响抖音**——任何带非 ASCII 的直链下载都会以同样方式崩。

### 根因 5：抖音 `filter_list` 被丢弃

分享页的 `videoInfoRes` 里，服务端明确给出了失败原因。实测一个仅自己可见的视频：

```json
"status_code": 0,
"item_list": [],
"filter_list": [{
  "aweme_id": "7298145681699622182",
  "filter_reason": "status_self_see",
  "notice": "抱歉，作品不见了",
  "detail_msg": "因作品权限或已被删除，无法观看，去看看其他作品吧"
}]
```

但 `app/douyin.py:112-114` 只判断 `item_list` 空不空：

```python
items = (page.get("videoInfoRes") or {}).get("item_list") or []
if not items:
    raise DouyinError("分享页里没有找到视频条目（视频可能已删除）")
```

`filter_list` 完全没读。于是「仅自己可见」「审核中」「地区限制」「好友可见」
全部塌缩成同一句猜测性的「可能已删除」，用户依然无法判断是不是程序的锅。

### 根因 6：`DouyinDownloadTask` 的直链缓存从未生效

`app/direct_dl.py:200-219`：

```python
def run(self):
    for _attempt in range(2):
        if not self._play_url:              # ← 只有缓存为空时才给 self.url 赋值
            ...resolve...
            self.url = info["play_url"]
            self._name_hint = info["title"]
        if not self._play_looks_html():     # ← 检查的是 self.url
            break
        self._play_url = ""
```

当 probe 已经缓存了 `play_url`（`app/download_tab.py:593-599` 传入）时，
`self.url` **从来没被赋成 play_url**，仍是原始抖音短链。于是：

1. 预检 `_play_looks_html()` 检查原始短链 → 短链 302 到分享页 → 返回 `text/html` → 判定「链接已失效」
2. 丢弃缓存 `self._play_url = ""`，第二轮重新解析

实测走缓存路径依然打印「抖音解析中…」，证实缓存 100% 无效——
上一版加的「5 分钟时效缓存」是死代码，每次下载都白白多跑一轮短链展开 + 分享页解析。

**更危险的是这条分支**：`_play_looks_html()` 的 `except Exception: return False`
（`app/direct_dl.py:195-196`）把「网络不确定」当成了「链接有效」。
预检请求一旦抖动（DNS/超时/SSL），立刻 `break`，然后 `super().run()`
拿着**抖音网页链接**去下载 → `DirectDownloadTask` 检出 `text/html` →
报「返回的是网页而不是媒体文件（链接可能已失效，或触发了网站的风控验证）」。
这是一条会真实失败、且报错完全指向错误方向的路径。

### 根因 7：失败不落日志

`app/proc.py` 的 `stderr_target()` 只接管子进程 stderr，`append_log()` 只在
`app/main.py` 的两个 excepthook 里被调用。而所有下载失败都走 `BaseTask.error()`
（`app/base_task.py:48`）直接上界面，**不落盘**。

实测翻了 894KB 的 `%LOCALAPPDATA%/ShiGuang/logs/app.log`，全是 ffmpeg 输出，
零条抖音 / 网络 / yt-dlp 记录。这与 CHANGELOG 里「报障从复现降为看日志」的目标不符。

### 根因 8：文案过度承诺

- `README.md:25`：`视频网站链接 | B站 / YouTube / 抖音 / X 等数千个站点`
- `app/download_tab.py:62`：`支持网站链接（B站 / YouTube / 抖音等）…`

实测口径是 9 个站点里 1 个免配置可用。文案把 yt-dlp 的理论覆盖面当成了本产品的实际能力，
而 YouTube / X 需要代理、抖音需要走自建解析、大量站点需要 cookie——这些前置条件一处都没提。

### 根因 9：yt-dlp 本身的覆盖边界（不可修）

- 快手 `Unsupported URL`：yt-dlp 已移除快手 extractor
- 好看视频 `Unsupported URL`：从未有过 extractor
- 微博 `TypeError: 'NoneType' object is not subscriptable`：yt-dlp extractor 内部 bug，需上游修

这三类**改本项目代码解决不了**，只能把报错说清楚（见 P0-3），不要让用户以为是本地问题。

## 四、修复方案

### P0-1：Cookie 支持（`cookies.txt` 文件，不做浏览器自动读取）

**约束**：见 2.3，`cookiesfrombrowser` 在 Windows + Chrome 127+ / Edge 运行中均不可用，
不要实现成浏览器下拉框。只做文件路径。

1. `app/app_settings.py` 按现有 `QSettings` property 风格增加一项
   （对齐 `save_dir` / `dl_format` 的写法，不是 dataclass 字段）：

```python
@property
def cookie_file(self) -> str:
    return str(self.q.value("download/cookie_file", "") or "")

@cookie_file.setter
def cookie_file(self, v: str):
    self.q.setValue("download/cookie_file", v)
```

2. `app/ytdlp_dl.py` 的 `build_ytdlp_opts()` 增加入参并注入：

```python
def build_ytdlp_opts(quality, fmt, format_id=None, cookie_file=""):
    ...
    if cookie_file and os.path.isfile(cookie_file):
        opts["cookiefile"] = cookie_file
    return opts
```

`ProbeTask.run()`（`app/ytdlp_dl.py:119-125`）和 `YtdlpTask.run()`（`:207-223`）两处 opts 都要加。

3. 设置页新增「Cookie」行。注意 **`widgets.PathRow` 目前是目录专用的，不能直接复用**：
   `app/widgets.py:84` 的 `_pick()` 写死了 `QFileDialog.getExistingDirectory`，
   右侧按钮也是 `open_in_explorer(目录)`。建议给它加一个 `pick_file` 开关而不是新写一个组件
   （避免多出一套重复的行控件）：

```python
def __init__(self, label_text, getter, setter, changed=None,
             pick_file=False, file_filter="", parent=None):
    ...
def _pick(self):
    if self._pick_file:
        d, _ = QFileDialog.getOpenFileName(None, "选择文件", self._getter(), self._file_filter)
    else:
        d = QFileDialog.getExistingDirectory(None, "选择文件夹", self._getter())
    ...
```

   `pick_file=True` 时把右侧「打开文件夹」按钮换成 `reveal_in_explorer(文件)`
   （`app/utils.py` 里已有，能直接定位到文件）。调用处传
   `file_filter="Cookies 文件 (cookies.txt *.txt);;所有文件 (*)"`。

   旁边放一个「怎么导出？」的说明按钮，文案要点：
   - 用浏览器扩展（Get cookies.txt LOCALLY 等）导出，格式选 **Netscape**
   - 导出后**关闭对应标签页**，cookie 有效期通常几天到几周
   - 只读本地文件，不上传
4. 校验：`cookiefile` 指向的文件若解析失败，yt-dlp 会抛 `Cookie file ... is not valid`，
   需要在 P0-3 的映射表里覆盖。

### P0-2：代理支持 + 整体超时

**代理**：

1. `app_settings.py` 增加 `proxy_mode: str = "system"`（`system` / `manual` / `off`）和 `proxy_url: str = ""`。
2. 新增 `app/netenv.py`，读 Windows 系统代理（yt-dlp 不会替你读）：

```python
def system_proxy() -> str:
    """读 HKCU Internet Settings；未启用或读失败返回 ''。"""
    try:
        import winreg
        with winreg.OpenKey(winreg.HKEY_CURRENT_USER,
                r"Software\Microsoft\Windows\CurrentVersion\Internet Settings") as k:
            if not winreg.QueryValueEx(k, "ProxyEnable")[0]:
                return ""
            s = winreg.QueryValueEx(k, "ProxyServer")[0]
    except OSError:
        return ""
    if not s:
        return ""
    if "=" in s:  # "http=127.0.0.1:7890;https=127.0.0.1:7890" 形式
        for part in s.split(";"):
            k, _, v = part.partition("=")
            if k.strip().lower() in ("https", "http") and v:
                s = v
                break
        else:
            return ""
    return s if "://" in s else f"http://{s}"
```

3. 解析出的代理注入 `opts["proxy"]`（yt-dlp 支持 `http://` `socks5://`）。
   注意 `app/douyin.py` 用的是裸 `urllib.request`，**不会**自动走 yt-dlp 的 proxy 选项；
   抖音是国内站点，本来也不需要代理，但如果用户设了全局代理反而可能绕远——
   建议 `douyin.py` 显式加 `ProxyHandler({})` 强制直连，避免被 TUN/系统代理干扰。

**整体超时**：光有 `socket_timeout` 不够（实测 15s 配置下 YouTube 跑了 120s）。
在 `ProbeTask` / `YtdlpTask` 里加一个 wall-clock deadline，用 yt-dlp 的 progress hook 检查：

```python
deadline = time.time() + PROBE_TIMEOUT   # 探测建议 25s，下载建议 60s
def guard(d):
    if time.time() > deadline:
        raise yt_dlp.utils.DownloadError("解析超时")
```

探测超时后界面要明确提示「该站点响应超时，可能需要代理（设置 → 网络代理）」，
而不是让它默默转两分钟。

### P0-3：补全 `errors.py` 映射

在 `app/errors.py:17` 的 `KEYWORD_MAP` 里补（注意顺序：越具体的放越前面）：

```python
("fresh cookies", "该网站需要登录 Cookie，请在 设置 → Cookie 导入 cookies.txt"),
("cookies (not necessarily logged in) are needed", "该网站需要登录 Cookie，请在 设置 → Cookie 导入 cookies.txt"),
("could not copy chrome cookie database", "读取浏览器 Cookie 失败：请先完全关闭该浏览器再试"),
("failed to decrypt with dpapi", "Chrome 127+ 已禁用 DPAPI 解密，请改用扩展导出 cookies.txt"),
("is not valid", "Cookie 文件格式不正确（需 Netscape 格式 cookies.txt）"),   # 需收窄，见下
("no video formats found", "该网站未能取到视频流（可能需要 Cookie，或站点已改版）"),
("unable to download api page", "无法访问该网站接口（可能需要代理，见 设置 → 网络代理）"),
("transporterror", "网络连接失败（可能需要代理）"),
("unsupported url", "该网站暂不支持（yt-dlp 未收录，非本软件问题）"),   # 覆盖已有的宽泛版本
```

注意 `"is not valid"` 太宽，会误伤别的报错；实现时应改为在
`friendly_error()` 里先判 `isinstance(e, DownloadError) and "cookie" in low`，再给 cookie 文案。

另外补一条兜底规则：**凡是含 `github.com/yt-dlp/yt-dlp/issues` 的报错，
一律截掉 URL 部分**，不要把 GitHub issue 链接甩给普通用户。

微博那个 `TypeError` 属于 yt-dlp 内部崩溃，建议在 `friendly_error` 的
`TypeError`/`AttributeError`/`KeyError`/`IndexError` 分支统一给
「该网站解析组件出错（上游 yt-dlp 问题），可尝试更新或换链接」，
而不是现在的 `解析失败（TypeError）`。

### P1-4：修 URL 提取的非 ASCII 崩溃

两处一起改，一处治标一处治本：

**治本**——`app/douyin.py:147`，用正则捕获到的规范短链，丢掉尾部污染
（`SHORT_RE` 是 `re.match` 前缀匹配，`group(0)` 天然就是干净的短链）：

```python
m = SHORT_RE.match(u)
final = expand_short(m.group(0)) if m else u
```

**治面**——`app/url_detect.py` 的 `extract_urls()` 末尾对非 ASCII 做百分号编码，
对齐浏览器行为，避免同类崩溃出现在直链下载上：

```python
u = urllib.parse.quote(u, safe=":/?#[]@!$&'()*+,;=%~")
```

顺带在 `URL_RE` 的排除集里加入 `\u4e00-\u9fff`——抖音/B站的短链、BV 号、数字 ID
全是 ASCII，遇中文即断是安全的，能从源头避免污染。

### P1-6：修 `DouyinDownloadTask` 的缓存与预检语义

`app/direct_dl.py:176-219`，两个问题一起修：

```python
def __init__(self, task_id, url, save_dir, fmt="auto", play_url="", name="", parent=None):
    super().__init__(task_id, url, save_dir, fmt=fmt, name=name, parent=parent)
    self._origin_url = url.strip()               # 原始抖音链接，重解析时用
    self._play_url = (play_url or "").strip()
    if self._play_url:
        self.url = self._play_url                # ← 补这一步：缓存命中时让 self.url 指向直链

def _play_is_stale(self):
    """三态：True=确认失效需重解析，False=可用，None=网络不确定（不要误判为可用）。"""
    try:
        from .douyin import MOBILE_UA
        req = urllib.request.Request(
            self.url, headers={"User-Agent": MOBILE_UA, "Accept": "*/*"})
        with urllib.request.urlopen(req, timeout=20) as r:
            ctype = (r.headers.get("Content-Type") or "").lower()
            head = r.read(16)
    except urllib.error.HTTPError as e:
        return e.code in (403, 410)
    except Exception:
        return None                              # ← 关键：不确定时不要当成"有效"
    return "text/html" in ctype or head.lstrip()[:1] == b"<"

def run(self):
    resolved = bool(self._play_url)              # 缓存命中即视为已解析
    for _ in range(2):
        if not resolved:
            self._emit(event="started", name="抖音解析中…", resumed=False)
            try:
                from .douyin import resolve
                info = resolve(self._origin_url)
            except Exception as e:
                self.error(f"抖音解析失败：{e}")
                return
            self.url = info["play_url"]
            self._name_hint = info["title"]
            resolved = True
        if self._play_is_stale() is not True:    # None（不确定）放行，交给直链引擎报真实错误
            break
        self.url, resolved = self._origin_url, False   # 确认失效 → 下一轮重新解析
    else:
        self.error("抖音下载失败：播放链接已失效（两次解析均失败），请稍后重试")
        return
    super().run()
```

要点：
- 缓存命中时**不再打印「抖音解析中…」**，也不再白跑一轮解析（实测现在每次都会）
- 预检的 `except Exception` 从 `return False`（当成有效）改为 `return None`（不确定），
  由调用方决定放行还是重试，杜绝「拿网页链接去下载」那条错误路径
- 预检 UA 从 `"Mozilla/5.0"` 换成 `douyin.MOBILE_UA`，与解析侧保持一致
- 新增 `self._origin_url` 保存原始抖音链接；原代码第二轮直接用 `self.url` 重解析，
  而 `self.url` 此时已被覆盖成失效的直链，重试必然再次失败
